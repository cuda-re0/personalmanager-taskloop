## 1. 文案纪律（先读这条）

**界面上只允许出现两类文字：字段值，和本文件列出的固定标签。**

不允许出现：解释性副标题、使用提示、玩法说明、"系统判定""AI 认为""提示：…"这类旁白、emoji 装饰、图例注释。

需要新增任何固定文案（按钮名、空状态文字、错误提示）→ 先在本文档登记，再实现。不要自己发挥，这是本项目最容易引起返工的地方。

**`aria-label` 不受本条限制。** 它是给屏幕阅读器读的，不显示在界面上、不占视觉空间，可以为控件写描述性标签（如"难度""时长""附件"）。但它不该变成第二套文案体系——只说明这个控件是什么，不解释怎么用。

**状态中文名（已登记，2026-10-28）**：

| 值 | 显示 |
|---|---|
| `todo` | 待办 |
| `doing` | 进行中 |
| `pending_review` | 待提交（v0.38） |
| `reviewing` | 待确认 |
| `done` | 已完成 |
| `missed` | 未完成 |
| `discarded` | 已丢弃 |
| `archived` | 已归档 |

这组词会出现在错误消息里（如「任务不能从「待办」直接变为「已完成」」），W6 的右栏 ① 区也会用到。权威实现在 `src/main/db/stateMachine.ts` 的 `LABEL`，改词要两边同时改。

**显示格式（已登记，2026-10-28，W6B 日历交付时补）**：

| 场景 | 格式 | 例子 |

| 月份标题 | `{YYYY} 年 {M} 月` | `2026 年 10 月` |
| 星期列头 | 单字，周一起 | `一 二 三 四 五 六 日` |
| 日浮层标题 | `{M} 月 {D} 日 周{X}` | `10 月 27 日 周二` |
| 日浮动层行尾分值 | `{N} 分`；整数不带小数位，小数最多 2 位 | `50 分`、`11.5 分` |
| 类型标签 | 与 §4① 同源 | `每日` / `限时` / `活动` |

这五条是**格式**不是文案，仍受本节第 10 行约束：不许在它们外面再包解释性文字（如"当月共 3 项""点击查看详情"）。

**错误消息也算界面文案。** `AppError.message` 是面向用户的中文短句，可直接渲染（02 §1），但它的模板必须先在本节登记。允许的动态成分只有三类：上表的状态中文名、任务标题、日期字段的中文名（如「起始日」）。`retryable` 字段已经表达了能不能重试，文案里不要再写"请重试""操作失败"。

## 2. 主窗布局

窗口：默认 `1440 × 920`，最小 **`980 × 560`**（v0.21 从 680×520 上调到 940；v0.26 因右栏 400 → 460 再上调 40，保证左栏不低于自己的 `min-width: 520`），`backgroundColor` 跟随主题，无自绘标题栏（用系统标题栏，避免拖拽区与输入框冲突）。

```
┌───────────────────────────────────────────────────────────────┐
│  顶栏 56px：左 应用名 · 中 (空) · 右 [悬浮条开关] [设置]        │
├──────────────────────────────────┬────────────────────────────┤
│                                  │  ① 当前任务        (弹性)   │
│   会话区  flex:1  min 520px       │  ─────────────────────────  │
│                                  │  ② 日历            (240px)  │
│   ┌─ 消息流（滚动）────────────┐  │  ─────────────────────────  │
│   │ 气泡 / 草稿卡片 / 审核卡片  │  │  ③ 积分            (120px)  │
│   └────────────────────────────┘  │  ─────────────────────────  │
│   ┌─ 输入区 固定 96px ────────┐  │  ④ 明细            (弹性)   │
│   │ [+] [多行输入]      [发送] │  │                            │
│   └────────────────────────────┘  │  w = 460px 固定（v0.26）    │
└──────────────────────────────────┴────────────────────────────┘
```

右栏宽 `400px` 固定，四区块纵向堆叠，各区块上下分隔线 `1px`。①④ 弹性、②③ 固定高。整栏可整体隐藏（右侧边界拖拽或顶栏开关）。

## 3. 会话区

### 3.1 气泡

| role / kind | 视觉 | 备注 |
|---|---|---|
| user / text | 右对齐，主色浅底，圆角 14，max-width 78% | 图片在上、文字在下，图最多 4 张九宫格 |
| assistant / text | 左对齐，无底或极浅底，圆角 14 | 支持 markdown：段落、有序/无序列表、行内代码、粗体 |
| assistant / task_draft | 卡片组，宽度撑满 88% | 见 §3.2 |
| assistant / task_review | 单张卡，左侧色条表示 verdict（pass 主色 / partial 琥珀 / need_evidence 蓝 / fail 灰） | 见 §3.3 |
| system / reminder | 居中细条，无气泡，`14px` 次级色文字 | 点击跳转对应任务 |
| system / error | 左侧灰底卡，带 `[重试]` | 不阻断会话 |

**渲染时按 `meta.kind` 收窄，不要按 `Message.kind`。** 两者是两个独立字段，且名字并不一一对应：`kind: 'text'` 的消息其 `meta` 是 `{ kind: 'none' }`（`MessageMeta` 里没有 `'text'` 成员）。用外层 `kind` 去 switch 会在 `text` 这一支上取不到任何 meta 字段。逐条映射：

| `Message.kind` | `Message.meta.kind` | meta 携带 |
|---|---|---|
| `text` | `none` | 无 |
| `task_draft` | `task_draft` | `drafts` |
| `task_review` | `task_review` | `taskId` / `verdict` |
| `reminder` | `reminder` | `reminderId` / `taskId` / `title` / `fireAt` |
| `error` | `error` | `code` / `message` / `retryable` |

### 3.2 草稿卡片（核心组件）

一张卡片 = 一个 `TaskDraft`。同一消息内多张时纵向排列，间距 12px。

```
┌──────────────────────────────────────────────┐
│  [每日·限时·活动 三选一]                      │  ← 顶部一行类型切换
│  标题（可点击就地编辑）              [+ 20]   │  ← 右上角是分值徽标
│  detail_md（最多 3 行，超出折叠）              │
│  ─────────────────────────────────────────    │
│  ○ 步骤 1                                     │
│  ○ 步骤 2                                     │
│  ─────────────────────────────────────────    │
│  [难度 ▾] [30 分钟] [10-30 18:00]  [丢弃][确认]│
└──────────────────────────────────────────────┘
```

类型切换会改变第三行的时间控件：

| type | 时间控件 |
|---|---|
| 每日 | `21:00`（每日提醒时刻）+ 可选结束日期 |
| 限时 | `10-30 18:00`（截止时刻） |
| 活动 | `10-30 09:00`（发生时刻） |

上表是**显示格式**。`TaskDraft.dueHint` 字段本身存完整 ISO8601（02 §2），渲染层负责 ISO ↔ `datetime-local` 的时区换位。**不要为了显示方便把年份截掉再写回字段**——跨年时会错一年，而 `dueAt` 同时喂提醒、逾期判定、效率系数三条链路。「补当前年」这种猜法一律不许用。

切换类型时，`reminderOffsets` 自动换成该类型默认值（限时 → 前 1 天/前 1 小时；活动 → 前 7/3/1 天），并在卡片下方以只读小字列出触发点，例如 `前 1 天 · 前 1 小时`。用户可在任务详情里改。

难度下拉的显示名（已定稿，2026-10-28）：

| 值 | 显示 |
|---|---|
| `trivial` | 琐事 |
| `easy` | 简单 |
| `medium` | 中等 |
| `hard` | 费劲 |
| `epic` | 大工程 |

下拉选项与卡片上的难度标签都用这一组，**不显示英文原值，不附加括号或说明**。除此之外不加任何难度描述文字（如"预计 30 分钟以内"）。

**下拉里实际可选哪几档，由类型决定**（`src/shared/taskRules.ts` 为唯一来源，不要在组件里另写一份）：

| 类型 | 下拉里出现的选项 |
|---|---|
| 每日 | 琐事 / 简单 / 中等 |
| 限时 | 简单 / 中等 / 费劲 |
| 活动 | 中等 / 费劲 / 大工程 |

切换类型时若当前难度不在新类型的可选项里，用 `snapDifficulty` 归位到最近一档（平手取低档），并**跟着重算分值**。

交互规则：

- 标题、类型、难度、时长、时间五项**可就地修改**。
- **改难度后**分值即时刷新，本地按 `@shared/points/rubric` 算，不调 `points.preview`（那是 IPC，W2 接线后才可用；且纯计算没必要过进程）。
- **改时长不影响分值**。v0.9 起时长已退出积分公式（02 §5.2），它只用于 AI 判难度、排提醒、算逾期。原来是"改难度/时长后刷新"，那句话已废。
- `missing_info` 非空时，在卡片底部以「待补」标签逐个列出，**不加任何引导语**。
- `confidence < 0.5` 时，卡片左边框变虚线（视觉弱提示，不写文字）。
- 确认 → `ai.confirmDraft` → 卡片变为已确认态（变灰、按钮消失、显示任务 id 关联），不可再改。
- 丢弃 → 卡片淡出移除，`ai.rejectDrafts`。
- 一个消息里 3 张卡片**独立处理**，不做批量确认。

### 3.2b 待提交卡片（v0.38 新增）

**点完成不再直接送审。** 右栏点 `[完成]` 后，任务进 `pending_review`，在会话流**末尾**（不是插进历史位置）生成一张待提交卡，等你交材料、再点提交：

```
┌──────────────────────────────────────────────┐
│ ▌ 交物理作业                      限时 · 20分 │  ← 左侧色条恒为 --accent
│──────────────────────────────────────────────│
│  证据： [pdf ×]                               │  ← 已传的证据，无 ×（证据不可删）
│  [+]                                          │  ← 与审核卡同一个隐藏 input
├──────────────────────────────────────────────┤
│                              [取消]  [提交]   │
└──────────────────────────────────────────────┘
```

规格（写死）：

| 项 | 规则 |
|---|---|
| 出现条件 | 该任务 `status === 'pending_review'`。**这是渲染层派生出来的卡，不是消息**——不落 `messages`，取消或提交后自然消失，历史里不留痕 |
| 排序 | 多张时按任务 `updated_at` 升序（先进的在上），整体排在所有消息之后 |
| 标题行 | 任务标题 + 右端 `{类型} · {N}分`（与审核卡同一套 `TYPE_LABEL` / `fmtPoints`），**不显示状态名、不显示"待提交"字样** |
| 无 `reason` 行 | 此时还没有 AI 结论，那一行整体不渲染。不许写"请提交证据""提交后由 AI 审核"这类说明 |
| 证据区 | 复用 `EvidencePanel`；`[+]` 常驻，`busy` 时禁用 |
| `[提交]` | 证据数为 0 时 **`disabled`**（灰、点不动，不加任何提示文字）；有证据才可点。点击 → `transition({to:'reviewing'})` → 跑审核（`runReview`） |
| `[取消]` | 点 → `transition({to:'doing'})`，卡片立即消失。**没有任何二次确认** |
| 超时 | 停留超过 **10 分钟**（自进 `pending_review` 起算，判据是 `updated_at`）由主进程自动退回 `doing`，卡片自行消失。**不是前端计时器**——窗口关掉也照样生效 |
| 请求进行中 | 提交后卡片就地转为"审核中"态：两颗按钮都 `disabled`、证据区 `[+]` 也禁用，**不新增"审核中…"文字**（沿用现有 `ai.status` 细环即可） |
| 失败 | 审核请求失败 → 任务回 `doing`、卡片消失、错误原文按现有规则落在右栏 ① 行内（不许留在卡上） |

**为什么不做成消息**：取消/超时都要"卡片消失"，落库就得再发明一种"已撤回的卡片"状态；而 `pending_review` 本身就是真值源，直接由状态派生最省，重启后也不会多出一堆悬空卡片。

### 3.3 审核卡片（S4 证据）

四条状态，卡片结构相同，动作区不同：

```
┌──────────────────────────────────────────────┐
│ ▌ 交物理作业                      限时 · 20分 │  ← 左侧 3px 色条 = verdict
│   截图显示已导出 PDF，含完整实验数据          │  ← reason，AI 的判断依据
├──────────────────────────────────────────────┤
│  证据： [pdf 角标] [缩略图]  [+]              │  ← 已有证据，只加不删（v0.35）
├──────────────────────────────────────────────┤
│                          [补证据] [重新审核]  │  ← 只有 need_evidence 有按钮
└──────────────────────────────────────────────┘
```

**证据标签显示什么**：`Attachment`（02 §2）目前只有 `id/kind/url/mime/bytes/width/height`，**没有 `name`**，所以标签上的是类型角标（`pdf` / `jpg`，取 mime 子类型），不是文件名。这不是偷懒——要显示 `报告.pdf` 就得给 `attachments` 加列、给 `Attachment` 加字段，那属于附件功能本身。在那之前**不要自己造一个 `name` 塞进 `Attachment`，也不要把完整 mime（`application/pdf`）直接显示出来**。

**v0.35 起动作区按「审核已自动流转」重排**——`pass` 由流程自动 `task.complete`，卡片出现时任务已是 `done`；`partial` / `fail` 已把任务送回 `doing` 或判 `missed`。所以除 `need_evidence` 外，卡片一律**只读**（没有任何按钮）：

| verdict | 色条 | 动作区 | 说明 |
|---|---|---|---|
| `need_evidence` | `--accent` 蓝 | `[补证据]`（无证据时）→ 有证据后 `[重新审核]` + `[补证据]`；**连续 3 次 `need_evidence` 后，最右再加一颗弱化 `[直接标记完成（不计分）]`**；最左恒有 `[取消]`（v0.38） | 唯一还要用户动手的状态：任务停在 `reviewing`，`reason` 处显示 `followup` |
| `pass` | `--accent` | **无按钮** | 已计分落库，不存在「再完成一次」 |
| `partial` | `--warn` 琥珀 | **无按钮** | 任务已回 `doing`，重新提交在右栏 ①；卡片内按 `verdict.gaps` 逐条列出未完成项 |
| `fail` | `--text-faint` 灰 | **无按钮** | 任务已回 `doing` 或判 `missed`，`reason` 是 AI 原话 |

**`[取消]`（v0.38）**：`need_evidence` 卡上点它 → `transition({to:'doing'})`，任务回进行中、不发分，卡片就地变只读（旧卡）。这是「我不想补了」的出口——之前只有连续 3 次后的「不计分完成」一条路，等于逼用户要么撒谎要么卡死。

四条附加规则（v0.35/v0.36）：

- **只有该任务最后一条审核卡的按钮有效**：同一任务补证据后重审会产生新的一条 `task_review`，更早的卡片只显示 `reason` / `gaps` / 证据，动作区为空。
- 请求进行中按钮 `disabled`，不出现第二份请求。
- 卡片动作失败（文件被拒、AI 未配置、网络错）时，在卡片动作区下方显示 `AppError.message` **原文**，2.6s 后消失；不另写句子。
- **`pass` 之后落库失败不能让任务卡在 `reviewing`**（v0.36）：`task.complete` 抛错时任务一律回 `doing`，同一张卡片显示错误原文。`pass` 卡永远没有按钮，所以这条兜底是唯一出口——不给 `pass` 卡加「重试」。
- **证据行的 `[+]` 只在任务还开着时出现**（v0.37，v0.38 加 `pending_review`）：`status ∈ {todo, doing, pending_review, reviewing}` 才渲染 `[+]` 与它的隐藏 file input；`done` / `missed`（以及 `archived` / `discarded`）一律不渲染。理由：`pass` 卡的任务已经完成、`missed` 已判失败，往这两个状态上追加证据没有任何出口（没有重审入口），只会让人以为还能补救；而 `partial` / `fail` 把任务送回 `doing` 时 `[+]` 必须留着——那是「补材料再提交」的唯一入口（右栏 ① 没有证据 UI）。
  这条让「除 `need_evidence` 外卡片只读」真正成立：`pass` / `missed` 卡上一个可点的东西都没有。

证据交互：

- 证据行末的 `[+]` 与动作区的 `[补证据]` **行为相同**：打开文件选择。文字证据（`kind:'text'`）不在 W7 范围。
- 图片证据存 `attachments`，卡片内显示 48×48 缩略图，点开大图；文件证据显示类型角标。
- **证据不可删（v0.35 裁决）**：主进程没有删除通道，所以卡片上**不显示**任何移除控件（原先的 `×` 已删）。加错的文件只能留着，等后续单补删除通道——不留「点了没反应 / 刷新即回来」的假按钮。

**两类任务在卡片上多一行（v0.7 积分改版的直接结果）：**

| 类型 | 增加的内容 | 文案 |
|---|---|---|
| 限时 | 右上角分值旁显示提前/逾期量 | `提前 4 天` / `提前 30 小时` / `逾期 3 天`，取不到 `completedAt` 时不显示 |
| 活动 | **无**（v0.35 撤掉结果档下拉） | 活动的 `result` 取 AI 在 verdict 里判的那一档，`pass` 时随 `task.complete` 一次写入。原先的 `[结果 ▾]` 依赖「点完成才计分」才有修改窗口，自动完成后这个窗口不存在，而 `task.update` 没有 `result` 字段——留一个改了没反应的下拉只会让人困惑。事后改结果档要另开通道，属新需求 |

活动的 `result` 取 AI 判定值（`verdict.result`，缺省 `met`），对应 ×1.2 / ×1 / ×0.85，见 02 §5.2。**不要给这三个词加解释**。
- 文字证据在卡片内单行显示，溢出省略号，点击展开。
- **`need_evidence` 状态下不允许绕过**：补完证据后卡片下方出现 `[重新审核]`，点了才重跑 AI。
- 连续 3 次 `need_evidence` 后，动作区右侧出现 `[直接标记完成（不计分）]`，弱化样式（`--text-faint`）。这是防死锁的出口，不是后门——点了就是不入账。

### 3.4 输入区

- 多行自适应，1~6 行，`Enter` 发送、`Shift+Enter` 换行。
- `[+]` 打开附件，或直接 `Ctrl+V` 粘贴截图、拖入文件。
- 粘贴图片后，输入区上方出现缩略图条，每张带删除角标。
- 发送后输入框清空、但**保留焦点**。
- AI 思考中：发送按钮变为禁用态并显示细环进度，输入框仍可输入（允许连打，队列化）。

#### 3.4.1 模式按钮（v0.37）

输入区一行从左到右：`[+]` → **`[模式]`** → 文本框 → `[发送]`。模式按钮**紧挨加号右侧**，两者间距与 `[+]` 到文本框的间距相同（8px）。

- **按钮文字恒为两个字：`模式`**，不随状态改变，不加图标、不加冒号、不加当前模式名。
- **当前模式只看底色**：

| 状态 | 视觉 |
|---|---|
| `task`（建任务，默认） | 实心 `--accent` 底、白字 |
| `chat`（聊天） | 无底色、`1px` `--border` 描边、`--text` 字色 |

- 尺寸与 `[+]` 完全一致（同宽同高、同圆角），点击后立即切换、**不做动画**（切换是状态不是过场）。
- 模式**不持久化**：每次启动回到 `task`。理由：建任务是主行为，聊天是附加；反过来会让用户第二天发一句话就被当成闲聊而不出草稿卡。
- 模式是**会话级状态**，切换时不清空已输入文字、不清空已选附件、不插入任何系统提示。
- `aria-label` 用 `模式`，`aria-pressed` 反映是否处于 `chat`。

> 这一节是 v0.37 唯一新增的界面文案（`模式`，已登记 §1.1）。除它以外，本单**不许**在界面上加任何文字：不加「当前：聊天」、不加提示条、不加角标、不加 tooltip。

#### 3.4.2 逐字显现（typewriter，v0.37）

**只对面向前端观感，不改请求协议**——主进程仍一次拿到完整回复并 `message.patch` 落库，渲染层负责把它"打出来"。

- 触发条件：`message.patch` 带来某条 `assistant` 消息的 `contentMd`，且该消息**在本次会话内从「空 / pending」变成有内容**。历史消息（`msg.list` 拉回来的）一律直接渲染，**不重放**。
- 速率：**40 字/秒**；本条总长 > 400 字时提到 **80 字/秒**。按 `requestAnimationFrame` 累加已显示字符数，不逐字 `setTimeout`。
- 打字期间每帧只更新该气泡的文本节点，**不重排整列表**（不许让上面的气泡跳动）。
- 用户在这条气泡上点一下 → 立即全显、停止打字。
- 打字期间不显示「正在输入」之类的新元素：等待阶段沿用现有细环（`ai.status: thinking`），开始出字后细环消失。
- 切走面板再回来：**不重放**，直接以完整文本渲染（判据同第一条的"本次会话内"）。
- 气泡内的 markdown 在**整段打完后**才解析；打字过程中按纯文本渲染（否则半截的 `**` 会闪）。

## 4. 右栏四区块

### ① 当前任务

按类型分三组，组间 12px 间距，组标题为：`每日` / `限时` / `活动`。空组不显示标题。

- **手动建任务入口（v0.21）**：面板顶部一个 `+` 按钮，点开就地展开一行表单，收起后回到 `+`。
  表单从上到下：`每日 / 限时 / 活动` 三选一 → 标题输入框 → `[难度 ▾] [时长] [时间控件]` → `[丢弃] [确认]`。
  - 时间控件随类型切换，与 §3.2 草稿卡同一套：每日 = `21:00`；限时 = `10-30 18:00`；活动 = `10-30 09:00`。
  - 难度下拉的可选项同样由 `src/shared/taskRules.ts` 决定，切类型时若当前难度对新类型非法，回落 `medium`。
  - 提交走 `task.createManual`（`type` 在顶层，其余条件进 `patch`）；成功后表单收起清空，列表由 `task.created` 事件刷新，**不做本地乐观插入**。
  - 这里**不支持**填步骤 / 详情 / 提醒偏移：步骤要建子任务（多次写入），归草稿卡那条链路，手动入口不重复实现。
- **每日组**：每行 = 一个今日 occurrence。左侧圆形勾选框、标题、右侧连续天数（`7` 这样的纯数字，不带"天"字以外的修饰）。
  - **只列今天那一天**（v0.21 强制）：`ensureRange` 会预生成今天~+3 天的 occurrence，混进来就是同一任务 4 行，用户逐个点掉等于给未来日期提前打卡。`groupTasks` 与两个渲染层 hook 都要按 `day === today` 过滤。
- **限时组**：状态点、标题单行截断、右侧显示剩余时间（`2h` / `明天` / `逾期`）。
- **活动组**：同限时，右侧显示距发生时间的倒计时（`7d`）。
- 组内排序：doing 优先 → priority 降序 → 时间升序（null 最后）→ sortKey。
- **今日已完成保留（v0.27 用户裁决「已完成的变淡显示」）**：
  - 每日组列今天**全部** occurrence（pending + done）；限时/活动组保留 `done` 且 `completedAt` 为今天的任务。已完成行**沉底**（组内活跃行在前）、整行 `opacity: .5`、无 `[完成]` 按钮、右列剩余时间/倒计时留空、每日勾选框已勾且 `disabled`、连续天数照常。
- **未完成（`missed`）显示（v0.34 立规，v0.35 修口径）**：审核驳回且已过截止时间的限时/活动任务落到 `missed`，
  与 `done` **同档处理**——沉底、整行 `opacity: .5`、无 `[完成]` 按钮、右列留空。
  **不加任何文字**（不写「已失败」「超时」）、不加删除线、不加颜色标记。分数不变。
  - **跨天自动消失**：`missed` 没有 `completedAt`，过滤口径是 **`updatedAt` 落在今天**（那一行是"今天被判失败"的）。`done` 仍按 `completedAt` 判。两者都靠渲染层过滤实现，禁止任何清理或定时删行逻辑。
  - 每日组的 `missed` / `skipped` occurrence **不显示**（v0.27 裁决：用户只要求已完成变淡；漏卡要显示另议）。done 行不额外禁拖拽，详情里的步骤照常可勾。
  - 不加删除线、不加「已完成」文字、不加 tooltip。
- 组间固定顺序：每日 → 限时 → 活动。每日在最上，因为它每天都得看一眼。
- **右栏比例配额 + 分割线（v0.29，用户裁决：废弃 v0.28 的「下固定、上吸差」模型）**：
  右栏被一条**可拖分割线**（位于 ① 与 ②③④ 之间）分为上下两半，两侧高度按比例分配、各自**内部滚动**：
  - 上半 = ① 任务区；下半 = ②③④ 整块（块内 ② 日历仍固定 240px，③④ 吃块内剩余、内部滚动）。
  - 拖动改变比例；**静止后窗口高度变化时上下比例不变**——两侧按同一比例伸缩，
    不许回到「一侧定高、另一侧吸差」。
  - 比例持久化：渲染层 localStorage（键 `taskloop.rightSplit`，存下半份额的小数），重启保持；
    默认 `0.71`（等价 v0.28 默认窗的观感）。读取时越界/损坏值按默认处理。
  - 拖动下限：上半 ≥ 160px、下半 ≥ 360px（日历 240 + 积分区最少可见 120），到限夹住、不回弹。
  - 分割线本身无文字、无图例（04 §7 文案纪律）；详情展开/收起**不许改变分割线位置**
    （详情高度全部由 ① 内部滚动吸收）。
  - ③④ 的日历层就地替换（v0.28 口径）不变，只是它随下半块按比例伸缩，不再定高 348。
- 点击行展开详情（`detail_md` + 步骤勾选 + 提醒偏移 + `[完成]`），就地展开，不弹窗。
- 步骤勾选只改子任务状态，不影响父任务；父任务 `[完成]` 时若还有未勾步骤，弹一个就地确认条（不是 modal）。
- 已完成的限时/活动不在此列表，进 ④。
- **完成被拒的反馈（v0.24）**：`task.transition` 或 `task.complete` 失败时，在该任务行内就地显示一行红字（`AppError.message` 原样），2.6s 自动消失。只有这一种反馈形式，不弹 toast、不弹 modal、不在页头汇总。

### ② 日历

月视图，7 列，高度固定 `240px`。顶部一行：`‹  2026 年 10 月  ›`。

**格子结构**

```
┌──────┐
│  27  │   ← 日期数字，14px
│   ·  │   ← 红点行，固定 6px 高，即使没点也占位（防止有/无红点的格子高度跳动）
└──────┘
```

- **红点**：该日有任务时，日期下方出现一个 `4px` 实心红点，颜色 `--dot:#E5484D`。
- 该日任务**全部完成**时，红点变为同色**空心圈**（`border:1.5px solid`，内部透明）。这条是我加的：否则一个月过完，日历全是红点，看不出"哪天真的干完了"。**如果你不想要，去掉即可，不影响结构。**
- 一天有多个任务仍是**一个点**，不叠加 —— 点数量在 7 列窄格里根本看不清。
- 今日格：数字加粗 + 1px 边框。
- 非本月日期：不显示（不填充上月/下月灰字），保持视觉干净。
- 空白日：只有数字，无点。

**点击日期 → 展开当日任务**

点击任意有任务的日期，从日历块底部**以浮层方式**展开一个列表（宽 400px、最大高 200px、内部滚动、带阴影、覆盖 ③④ 区域，不挤压布局）。点击外部或再点同日收起。

```
┌────────────────────────────────────┐
│ 10 月 27 日 周二               ×   │
├────────────────────────────────────┤
│ 18:00  交物理作业   限时  ·  23 分 │
│ 09:00  英语六级考试  活动  ·  50 分 │
└────────────────────────────────────┘
```

- 每行：`时间 · 标题 · 类型标签 · 分值`。已完成的行标题加删除线、整体降透明度。
- **分值的语义是"计划/实得原值"，渲染层不重算、不做标记**（v0.18）：`calendar.dayDetail` 对已完成项给 `points_awarded`、未完成项给 `points_planned`，两者可能不等（质量/效率系数），列表只照原值显示。要区分两者得新增登记文案，本轮不做。
- **v0.28 裁决：浮层整体作废**（`66a9664` 的贴行定位方案一并作废）。点某天时，
  下方的 ③④ 积分面板**整块替换为「日历层」**——就地替换，不弹层、不覆盖：
  该日任务列表（沿用 `occurrence.listByRange(day, day)`），每行 = 完成状态勾
  （空心=未完成、实心=已完成）+ 任务标题，**不加**完成/未完成文字与统计。
  点行 → 高亮 ① 对应任务（日历层不关）；**再点同一天 = 关闭**回积分面板；
  点其他天 = 内容切换。没有选中的日子时不发请求（零请求原则）。
- 点击行 → 右侧 ① 区滚到该任务并短暂高亮。
- **任意日期可点（v0.21 改）**：所有格子都是可点控件，包括无任务的日子。原口径「空日期点击不响应」（≤v0.20）作废——用户要的是「点哪天就看哪天」，没任务也要能点开、看到当天空白。
- **空态**：点开后 `dayDetail` 返回空时，**保留浮层标题（`10 月 27 日 周二`）+ 关闭按钮，列表区留白**，最小高度 40px 防止浮层塌成一条线。不出现"暂无任务"之类文字（§7 空状态留白原则）。空日期依然不画红点，红点只表示「这天有任务」。

**数据来源**：`calendar.dayIndex(year, month)` 一次取当月红点，`calendar.dayDetail(day)` 点击时才查。**不允许**渲染层为 30 个格子各发一次请求。

**日历只呈现限时与活动。** 每日任务不进日历、不点红点（Q2 已定），它们归 ① 区的「每日」组和会话管理。实现方不要"顺手"把 occurrence 混进 `dayDetail`，那会让日历变成一片红。

### ③ 积分

- 大数字：当前余额，`32px/600`。
- 右侧两行小字：`今日 +N`、`本周 +N`。
- 下方一条 7 日迷你柱状（无坐标轴、无图例）。
- 无任何说明文字。

**分值显示格式（全界面统一，写在 `shared/format.ts` 的 `fmtPoints()` 里，不许各处自己 `toFixed`）：**

| 实际值 | 显示 | 不显示 |
|---|---|---|
| 23 | `23` | `23.00` |
| 10.75 | `10.75` | `10.8` / `10.750` |
| 5.5 | `5.5` | `5.50` |
| -10.75 | `-10.75` | `-10.8` |

规则：最多 2 位小数，末尾的 0 去掉。因为积分是小数（02 §5.2），界面上任何"取整显示"都会让余额和明细对不上——用户会认为账算错了。

**实现约束**：`fmtPoints` 的唯一实现是 `String(roundPoints(v))`，复用 `rubric.ts` 的 `roundPoints`，不要在里面另写 `Math.round` 或 `toFixed`——"全项目 `Math.round` 只准出现在 `roundPoints` 内"这条禁令同样管格式化函数。`String()` 天然去掉尾零，不要再额外裁剪；输入若已过 `roundPoints`，也不会出现 `5.750000000000001` 这类尾巴。

### ④ 明细

- 时间倒序流水：`HH:mm  标题或原因  ±N`，`±N` 用上面的 `fmtPoints`。
- 正数用主色，负数用灰红。
- 顶部一行四个分段标签：`今日` / `本周` / `本月` / `明细`，同一套样式（segmented，无说明）。前三个切**数据范围**，第四个切**视图**。
- 点击条目 → 若有 `taskId`，滚动并高亮对应任务（任务在右栏 ①，不切视图、不滚走）。**高亮是条件行为**（v0.26 澄清）：能产生流水的完成动作，多数会让任务当天从 ① 消失——限时/活动的 `done` 不在活跃状态、每日组只渲染当天的 `pending` 打卡。这类行的点击是**空操作**（事件照发，① 没有目标就不动）；任务在 ① 中（如撤销后回 `doing` 的、将来审核停在 `reviewing` 的）才可见高亮。**不许**为了「让高亮总能被看见」去改 ① 的过滤条件——那是 ① 的语义（§4①）。
- 行结构（v0.26 简化）：整行是一个按钮（点它跳任务），行内只有三样——时刻、标题、分值。没有第二个按钮。
- **不提供撤销**（v0.26 用户裁决：「撤销这个功能去掉，不需要」）。流水只读；主进程的 `task.undo` 通道**保留**（数据层、通道、既有测试都不动），只是界面不再有入口。
- 已冲销行整行 `opacity: .5`（历史数据里可能有），不另加文字、不加 tooltip。
- **右侧留白**：③④ 的内容距面板右边缘 **20px**（原 16px，视觉上贴着窗口边）。行内一律允许收缩（`min-width: 0`），任何一行不许横向溢出、不许出现横向滚动条。

**明细视图（v0.26，取代 v0.24 的整窗明细页）**

`明细` 是 ④ 的第四个标签，**在面板里就地换内容**——不跳页、不覆盖、不新增视图状态：

- 选中 `明细` 时，③ 积分（大数字 + 柱状）以下的整块区域替换为明细视图；`今日 / 本周 / 本月` 三个标签保持可见可点，点任一个回到平铺流水。
- 明细视图内部（自上而下，滚动只发生在这一块里，外层不滚）：
  - **月导航**一行，高 32px：左 `‹` / 中 `2026年10月` / 右 `›`；行尾当月净额（`fmtPoints` + 符号，正数主色、负数灰红）。
  - **按 `day` 分组**：组头 `10月28日` 吸顶（背景 `--bg`、`12px`、`--text-faint`），组内按 `createdAt` 降序。
  - 行高 32px = `HH:mm` + `reasonText`（超长省略号）+ `±N`。
  - 已冲销行整行 `opacity: .5`。
  - 空月份只留空白列表区（§7）：**不写「今天」「昨天」「暂无记录」**。
- 翻月判据（v0.25 沿用，务必别退回旧写法）：**落月不得晚于本月**。`‹` 无最早边界（可以一直往回到空月）；到达当月 `›` 即 `disabled`。「当前月是不是本月」（按钮灰不灰）与「落月是不是未来月」（这次翻月算不算数）是**两个问题**，不得用同一个谓词。
- 数据来源：流水取 `points.ledger({ from: 月初, to: 月末, limit: 500 })`；当月净额取 `points.monthStats` 求和（**不用 ledger 求和**，`limit` 会截断）。
- **没有视图要提升**：`明细` 的选中态只活在 `PointsPanel` 内部。`renderer/main/index.tsx` 不再有 `view` 状态、不再挂 `LedgerPage`、不再有整窗覆盖层——左栏会话区因此永远不需要"隐藏 / 恢复"，v0.24/v0.25 那套覆盖层与 `visibility` 的讨论**整体作废**。

## 5. 悬浮窗规格（v0.30 重做）

独立 `BrowserWindow`，透明、置顶、无边框、不进任务栏。**尺寸与坐标全部由主进程 `hudService` 决定**，
渲染层 CSS 只负责画（`width/height: 100%`），不许用 CSS 改窗口大小。

### 5.1 基础窗体参数

```ts
new BrowserWindow({
  width, height,                       // hudService 算，见 §5.2
  frame: false,
  transparent: true,
  backgroundColor: '#00000000',
  resizable: mode === 'panel',         // 球固定 56×56，面板可拉伸
  movable: true,
  minWidth: 280, minHeight: 320,       // 仅 panel 生效
  maxWidth: 720, maxHeight: 900,
  skipTaskbar: true,
  alwaysOnTop: true,
  hasShadow: false,
  roundedCorners: false,
  focusable: true,
  show: false,                          // ready-to-show 后再显示，避免白闪
  webPreferences: { preload, contextIsolation: true, sandbox: true },
})
win.setAlwaysOnTop(true, 'pop-up-menu')   // 不用 'screen-saver'，否则盖住全屏视频
win.setVisibleOnAllWorkspaces(true)        // macOS 有效，Windows 无副作用
```

### 5.2 两种形态

| 形态 | 尺寸 | 位置 |
|---|---|---|
| `ball` 长条 | `132 × 40` | **初始贴屏幕右边缘**（`x = workArea.right − 132`）、`y = 10%`；之后可自由拖动（x/y 都动），clamp 进工作区（长条自身不出屏） |
| `panel` 面板 | 默认 `360 × 480`，**用户可拉伸** | 自由位置 + 拉伸后的尺寸；**纵向 clamp 进工作区，横向允许出屏**（见下） |

- **首次启动**（`hud.position` 为空）：`ball`，`y = workArea.y + workArea.height × 0.1`。
- **记忆**：位置落 `hud.position`、面板尺寸落 `hud.size`，重启恢复。
- 形态切换三条路径：
  1. **点按**长条 → 面板；**长按**长条 → 拖动（见 §5.2.2）；面板内 ESC → 长条。
  2. **松手才判形态**（v0.32 用户裁决「移动时不需要改变状态，改变状态只有点击和位置判断」）：
     拖动过程中**形态一律不变**，松手时判一次：
     - 长条态：距左/右边 `> 工作区宽度 × 1/8` → 展开成面板。
       （v0.31 的固定 `48px` 作废——用户裁决「超过屏幕的 1/8 就展开」；1920 宽屏即 240px。）
     - 面板态：**左右出屏宽度 > 面板宽度 × 1/3** → 收成长条，**贴在出屏的那一侧**；
       `≤ 1/3` 时**保持原位置不动**（允许部分出屏，不推回屏内。v0.31 用户裁决）。
     - 出屏宽度按 `max(0, workArea.x − rect.x)`（左）与 `max(0, rect.right − workArea.right)`（右）算，
       **不取两者的 min**，比的是"哪一侧真的露在外面"。
  3. 判定时机分两条路：长条态由渲染层 `end:true` 直接触发（**没有 120ms 去抖**）；
     面板态仍走 `move` 去抖 `120ms` + `settle` 补判（原生拖动拿不到松手事件）。
     程序化 `setBounds` 产生的回声必须丢弃（比对目标 bounds 与当前 bounds 的 x/y），否则会无限自我切换。
- 面板拖动把手 = 头部那一行（`-webkit-app-region: drag`）；列表、tab、输入、设置控件一律 `no-drag`。
- 拉伸：原生窗口边缘（`resizable: true`），`resize` 收尾时落 `hud.size`；长条态 `resizable: false`。

#### 5.2.1 长条内容（v0.31）

从左到右三段，垂直居中，整条 `border-radius: 999px`：

| 段 | 内容 | 说明 |
|---|---|---|
| 左 | 进度环 `20 × 20` | conic/stroke 环，比例 = `done / total`（`total = 0` 时为 0，不除零）。**与 v0.30 圆球上的环同源**，只是缩小 |
| 中 | `3/8` | `done/total`，与面板头部同一 `ratioLabel` |
| 右 | `周五` | 当天星期，硬编码数组 `['周日','周一','周二','周三','周四','周五','周六']`，不依赖 locale |

- 字号 `12px`，数字用等宽（`font-variant-numeric: tabular-nums`），免得分母变化时抖动。
- 段间距 `6px`，左右内边距 `10px`；环与文字不同色：环用 `--accent`，文字用 `--text`。
- **手势（v0.32 用户裁决「点按点击，长按拖动」）**：整条 `no-drag`，由渲染层自己判手势，见 §5.2.2。
  **不再用 `-webkit-app-region: drag`**——drag 区收不到任何鼠标事件，做不到「既点又拖」。

#### 5.2.2 长条手势（v0.33：按下即预备拖动）

用户原话：「点按点击，长按拖动」「移动时不需要改变状态」「放上去鼠标样式不要变，那个小手不好看」
「直接上去就能拖动的手感，而不是还要停留一会」。

**没有时间阈值**：按下就是预备拖动，只由**位移**决定点按还是拖动。

| 阶段 | 条件 | 结果 |
|---|---|---|
| 按下 | 主键 | 预备拖动：调一次 `hud.dragBegin()` 取左上角算 `grabOffset`；**窗口不动** |
| 移动 | 位移 `≤ 4px` | 仍不动（点按预备，窗口一个像素都不许抖） |
| 移动 | 位移 `> 4px` | 进入拖动，此后窗口**贴着光标**走（不等任何时长） |
| 松开 | 从未超过 4px | 展开成面板 |
| 松开 | 已拖动 | 发 `end: true`：落库 + 判一次形态 |
| 取消 / 丢捕获 | 拖动中 | 与松开同一套收尾（`end: true`：落库 + 按最终位置判一次形态），但**不触发点按展开** |

常量：只有 `TAP_TOLERANCE = 4`（`hudModel.ts` 导出）。原 `LONG_PRESS_MS` 已删——
「按住多久才算拖动」正是手一停就发涩的原因。

**拖动必须是绝对定位，不许用增量累加**（v0.32 修正）：

- 按下瞬间调一次 `hud.dragBegin()`，拿回长条当前左上角 `{x,y}`；
  记 `grabOffset = { 按下时 screenX − x, 按下时 screenY − y }`。
- 之后每个 `pointermove` 算**绝对目标**：`{ x: e.screenX − grabOffset.x, y: e.screenY − grabOffset.y }`，
  直接发给 `hud.dragTo({ x, y, end: false })`。
- 理由：`setBounds` 是异步的，上一版「读当前 bounds + 加增量」会读到旧位置，增量一帧帧漏掉/错位，
  表现就是「窗口不跟光标、越拖越偏」。绝对目标每帧重新对齐光标，丢帧也不会累积误差。
- `dragBegin` 返回前收到的 move 只更新基准、不发送（避免用未就绪的 `grabOffset` 甩一下窗口）；
  `grabOffset` 一就绪，若已在拖动中，立刻按**最新**指针补发一帧——不要让 IPC 往返吞掉头几帧。
- 每帧最多一次 IPC：`pointermove` 只更新目标点，`requestAnimationFrame` 里发一次。
- 松手时把当前目标点连 `end: true` 再发一次（主进程据此落库并判形态）。
  从没移动过（`grabOffset` 还没回来就松手）则不发送。

其它约束：

- 整条 `.hud-ball` **不写** `-webkit-app-region`（没有 drag 区）；`.hud-hit` 保留覆盖全条的 `inset:0` 承接
  pointer 事件与 `aria-label`，但**不许挂 `onClick`**（点击只由 `pointerup` 判定）。
- `pointerdown` 里 `setPointerCapture(e.pointerId)`；`pointerup` / `pointercancel` / `lostpointercapture`
  共用一个收尾函数，`gesture = null` 要在发 `end` 之前置位，避免丢捕获时二次发送。
- 位移一律用 `e.screenX/screenY`（`clientX` 会随窗口移动漂）。
- **鼠标样式全程不变**：不写 `cursor: pointer` / `grab` / `grabbing`，保持系统默认箭头。
  拖动中也只有窗口在动，不加任何视觉状态。
- 面板态不改：仍靠 `.hud-head` 的原生 `drag`。`.hud-grow` 保持 `min-width: 24px`，
  保证面板拉到最窄（280）时头部仍有可抓空白。

### 5.3 页结构（v0.30）

面板内两页，头部两个 tab，**文字只有** `今天` / `设置`（本节的标签即白名单，别的一个字都不许加）。
长条态另有 `3/8`（`ratioLabel`）与 `周一`…`周日`（星期表），除此之外长条上不许出现别的字。

**今天页**

- 头部：`● N/M` + `今日 +N`。
- 今日行：每日 occurrence + 今天到期的限时/活动；每行 = 完成控件 + 标题。**v0.38 改：只有每日行有完成控件**，见下。

**列表排序（v0.38，写死）**

行顺序 = 未完成区（每日 → 限时 → 活动）接已完成区（每日 → 限时 → 活动）：

1. 每日 occurrence（`status === 'pending'`），保持服务端顺序；
2. 限时任务（`type === 'deadline'` 且未完成），按 `dueAt` 升序、无 `dueAt` 的排最后；
3. 活动任务（`type === 'event'` 且未完成），同上；
4. 已完成区：先每日已打卡，再已完成的限时，再已完成的活动。区内的相对顺序沿用上面三条。

「已完成」= 每日 `occurrence.status === 'done'`，或任务 `status ∈ {done, missed}`。**完成即沉底，不留在原位**。

**行交互（v0.38，写死）**

| 行的种类 | 勾选控件 | 点击行 |
|---|---|---|
| 每日 occurrence | **有**，点击 → `occurrence.complete` | 无额外动作 |
| 限时 / 活动 | **不渲染勾选框**（整个圆圈节点都不进 DOM） | **绑了 onClick 但什么都不做**：不加 `disabled`、不变灰、不改光标、不加 tooltip |

- 限时/活动的行**只起提醒作用**，完成只能回主窗做。理由：HUD 上原来的勾走的是 `transition('reviewing') → task.complete`，**完全绕过 AI 审核直接发分**，与「必须过审才计分」冲突（v0.38 起这条路被移除，不是隐藏）。
- 已完成的限时/活动行：整行 `opacity: .5`（复用主窗 `task-row--done` 的视觉口径），不显示分值、不加「已完成」之类的字。
- 行列表**可纵向滚动**（`.hud-list { overflow-y: auto }`），不再按 6 行截断；行数超过可视高度就滚。**不加滚动条自定义样式、不加「更多」入口**。

- 完成失败（每日任务 `occurrence.complete` 失败）在该行**行内**显示 `AppError.message` 原样，4s 消失（与主窗同口径）。
- 行尾时间 / 分值仍不显示（v0.20 口径不变）。
- 保留「一句话加任务」输入（`task.createManual`，`deadline / medium / 无 due_at`，v0.17 口径）。
  **形态要求（v0.30 用户裁决）**：它是今天页**列表下方**的一行普通输入 + 提交按钮，
  不做 v0.21 那种贴着窗口顶边的横条（`dock-bar`），也不做成浮在列表上的覆盖条。

**设置页**（替代 v0.21 的右键菜单，**右键菜单不再实现**）

- 三项，文字固定：`背景颜色`（`<input type="color">`）、`透明度`（range `0.3–1` step `0.05`）、
  `关闭悬浮窗`（`hud.setVisible({ visible: false })`）。
- 前两项即时生效并落 `hud.background` / `hud.opacity`；关闭后从主窗顶栏开关再打开。
- 没有第四项：不加「重置」、不加说明文字、不加 tooltip。

### 5.4 背景与文字

透明度**只作用于背景**：渲染层把 `hud.background`（`null` → 主题 `--bg`）与 `hud.opacity`
合成 `rgba(r,g,b,a)` 写进 CSS 变量 `--hud-bg`；禁止把 `opacity` 加到容器上（文字会一起变淡）。

### 5.5 数据来源

与主窗同一份数据：`app.getBootstrap` 拿全量，之后只靠 `DomainEvent` 增量。**不读主窗的 store**。

**v0.38 补一条拉取**：`app.getBootstrap().tasks` 只含 `todo/doing/reviewing`（活跃三态），拿不到"今天刚完成"的任务，所以 HUD 首载时**并行**追加一次 `task.list({ status: ['done', 'missed'] })`，在渲染层按 `updatedAt` 是本地今天过滤后并入。不做这次拉取的话，主窗完成的任务在 HUD 上只会**消失**，永远做不到"变灰沉底"。

- 事件增量沿用 `task.created` / `task.updated` / `task.removed`。收到非活跃状态的 `task.updated` 时**不再从列表删除**，而是按上一条规则（今日则保留并标为已完成、跨日则移除）。
- `pending_review`（待提交）算活跃：HUD 要能看到"这条我今天点过完成但还没交材料"。

### 5.6 交互边界

允许：看今天、完成/打卡、一句话加任务、改背景颜色与透明度、关闭悬浮窗。
不允许：任务详情、日历、积分明细、新建带完整字段的任务。保持「一眼看完、一步操作」。

全屏自动隐藏仍不实现（v0.17 降级口径不变）：`hud.autoHideFullscreen` 的 key 与默认值保留、标注未实现，
不许写永远为 false 的假检测。

## 7. 空状态与错误态（文案需登记）

| 位置 | 条件 | 显示 |
|---|---|---|
| 会话区 | 无消息 | 一句话示例："发我一段话或一张图，我把它变成任务。"（**已定稿，照用**） |
| ① 当前任务 | 无任务 | 空，不显示文字 |
| ④ 明细 | 无流水 | 空，不显示文字 |
| AI 未配置 Key | 首次启动 | 输入区位置替换为单一 `[配置模型]` 按钮 |
| AI 失败 | 请求失败 | 会话内 error 气泡 + `[重试]` |
| 悬浮窗 | 无任务 | 收起态只显示积分，展开态列表区空白 |

除会话区那一句外，其余空状态**一律留白**，不写"暂无任务""快去添加吧"这类文案。

## 8. 响应式与多屏

- **窄窗（v0.21 改）**：右栏固定 `400px`、会话区 `min-width:520px`，两者相加 920 就是布局下限，因此主窗最小尺寸取 `940 × 560`。原先登记的「`< 1000px` 时右栏收起为 48px 图标条」**未实现且本轮不实现**——在没有图标条的前提下让窗口缩到 680 只会把日历挤成几列、出现横向滚动条。窄窗响应式如果以后要做，必须和图标条一起做。
- 悬浮窗跟随所在 `display` 的 `workArea`（不是 `bounds`，避开任务栏）。
- 显示器配置变化（插拔、分辨率改）时重算 bounds，越界则归位主屏顶部。
- DPI 缩放：所有像素值按 `devicePixelRatio` 由 Electron 处理，CSS 用 px 即可，但要测 125% / 150%。

## 9. 提醒的醒目程度（R15）

你要求"醒目"。醒目不等于"打断"——半夜弹个全屏遮罩会让人想卸载。所以做两级，默认第一级。

### 9.1 `normal`（默认）

触发时同时做四件事：

1. **HUD 变色 + 脉冲**：整条变 `--dot` 色，`2s` 内脉冲 3 次（`opacity 1→0.6`），若处于收起态则自动展开并保持 `8s`。
2. **会话注入**：会话流插入一条 `system/reminder` 居中细条，并自动滚到底（若用户正在输入则不抢滚动位置）。
3. **主窗提示**：若主窗处于最小化，`win.flashFrame(true)` 闪任务栏；若在前台，右栏 ① 对应任务行短暂高亮 `--dot` 描边。
4. **系统通知**：Windows toast，标题为任务标题，正文为偏移标签（如"前 1 小时"）。

### 9.2 `strong`（可选，需用户为单个任务开启）

在 `normal` 全部动作之上，追加：

- 一条横向横幅从屏幕顶部滑下（`height:64px`，全宽，`--dot` 底色），**不遮挡内容**，`15s` 后自动收，可手动 ✕。这是"醒目"但不阻塞的做法。
- 外部渠道强制发（即使该任务没配邮件 / 外部推送）。

**不做**全屏遮罩、不做必须点击才消失的模态、不做声音（除非以后单开一项）。理由：提醒的目的把人拉回来，不是惩罚他。

### 9.3 静默时段

`settings['reminder.quietHours']` 默认 `22:00–08:00`。落在其中的提醒：

- 不弹 toast、不推外部渠道
- 只在会话流留一条，HUD 不脉冲
- 顺延到 `08:00` 补一次 `normal` 提醒（只补最近的一条，不把整夜攒的 10 条一次刷出来）

### 9.4 提醒条目的样式

```
┌──────────────────────────────────────┐
│  ⏰  交物理作业 · 前 1 小时            │   ← 居中细条，14px，次级色
└──────────────────────────────────────┘
```

- 用 `--dot` 小圆点而非 emoji 图标，与日历红点同源。
- 可点击跳转到任务；hover 出现 `[稍后提醒]`（snooze 15 分钟）。
- 不加"别忘了""加油"这类文案，见 §1。
