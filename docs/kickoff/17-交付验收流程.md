# 交付与验收流程（v1）

> 从本轮起，**每一项工程都要走完三段才算完工**：施工方交付 → 架构方审核 → **用户验收**。
> 前两段可以内部完成，第三段必须由用户在真机上点。**用户没点头的项，一律记为"未验收"，不进下一浪的依赖链。**

---

## 一、三段的分工

| 段 | 谁做 | 产出 | 判定 |
|---|---|---|---|
| ① 交付 | 施工方（外部会话） | 代码 + 交付报告 + `git log` | 自检表全 ✅ |
| ② 审核 | 架构方（我） | 审核报告：逐条 PASS / P0 / P1 / P2 | P0=0 且 P1=0 才转③ |
| ③ 验收 | **用户（你）** | 一句话结论 + 问题截图 | 硬指标全过才收工 |

三段之间**不许跳**。特别是"我审完就直接算完工"——那是之前的老做法，HUD 那批问题就是这么漏出去的。

---

## 二、② 审核通过后，我会给你什么

一条**验收单**，固定五段：

1. **一句话说明这轮做了什么**（不超过三行，不带术语）
2. **前置条件**：哪个 commit、要不要重装、要不要清库、要不要造数
3. **手点清单**：编号 + 操作 + 期望现象，每条都可判定成败（不写"看起来正常"这种）
4. **已知不做的项**：这轮故意没做的，列出来免得你以为是漏了
5. **怎么反馈**：哪种情况算阻塞、怎么描述

---

## 三、③ 你需要做的步骤（固定动作，每轮都一样）

### 第 1 步：确认起点干净

打开 PowerShell，粘这一整行（**一行，不要分多行**）：

```powershell
cd C:\Users\shuiliang\WorkBuddy\任务管理审核; git log --oneline -1; git status --porcelain
```

- 输出第一行应等于验收单里写的 commit
- 第二行应该**什么都不输出**（工作区干净）
- 如果有未提交文件，先告诉我，别自己 `git checkout`

### 第 2 步：清环境变量（这一步不做，应用会出现 `protocol` 为 undefined 的崩溃）

```powershell
Remove-Item Env:ELECTRON_RUN_AS_NODE -ErrorAction SilentlyContinue; $env:ELECTRON_RUN_AS_NODE
```

最后一个表达式**必须没有输出**。有输出就再跑一次前半句。

> 这个变量是跑 seed / 测试脚本时临时设的，一旦漏在当前会话里，`npm start` 会让 Electron 以 Node 身份启动，报 `Cannot read properties of undefined (reading 'registerSchemesAsPrivileged')`。**那不是我改坏了代码**，按这步清掉即可。

### 第 3 步：构建并启动

```powershell
npm run build; npm start
```

- `npm run build` 的最后应该看到 `✓ built in …`，没有 `error TS`
- `npm start` 会再 build 一次（正常），然后弹出应用窗口
- 窗口没出来 / 白屏 / 报错 → **截图整段控制台**发我，别自己改代码试

### 第 4 步：按验收单手点

- 从第 1 条往后按顺序点，**不要跳着点**（有些条目依赖前一条留下的状态）
- 每点完一条，在心里记 `过 / 不过`；不要求你边点边写记录
- 需要造数时我会单独给命令（例如 `npm run seed`），没给就是不用造

### 第 5 步：报结果

全过就一句：

```
N 条全过
```

有过不掉的，按这个格式发我（**一条一段**）：

```
③ 期望：点流水行尾 [撤销]，余额回落
   实际：点下去没反应
   截图：xxx.png
```

**不需要你判断是哪个文件的问题，也不需要你提修法**——那是我的活。你只要给"操作 → 现象"。

## 四、我会怎么处理你的反馈

| 你报的现象 | 我的归类 | 后续 |
|---|---|---|
| 功能没生效 / 报错 / 闪退 / 布局塌 | **P0**，阻塞 | 出补丁开工词退回施工方，修完重新走②③ |
| 能用但别扭、文案不对、位置偏 | **P1**，不阻塞 | 记账，与下轮一起修 |
| "我本来想要的是另一种" | **契约错**，我改文档 | 先确认你的目标形态，再改契约、再派单 |

**P0 未清零，不进下一浪。** 这条是硬约束——否则问题会叠着问题，最后没人说得清是哪个版本坏的。

## 五、为什么要有第 3 段

过去几轮的事实（不是推测）：

- 395 条测试全绿、typecheck / lint / build 零错，你上手 5 分钟点出 **7 个问题**，其中 1 个是**往数据库里写了 4 天提前打卡**的真缺陷。
- 那次回归的原因是"每日组出现 4 行"——单元测试断言了 `ensureRange` 生成 4 天 occurrence（这是对的），但**没人断言这 4 行不该同时进"今日列表"**。
- 测试只能守"我以为的语义"，守不住"你没说出口的期望"。第 3 段就是补这一层。

---

## 六、每轮的验收清单由我写，不由施工方写

施工方的自检表只能证明"按他理解的需求做完了"。用户验收清单必须由**架构方**写，因为只有架构方同时知道：契约写了什么、这轮改了什么、哪些是老问题。

清单写法约束（我自己遵守）：

1. 每条必须是**可判定的**："点 A 之后 B 在 1 秒内变化"，不写"感觉流畅"
2. 每条给出**失败时的典型现象**，便于你对照
3. 需要造数的条目，命令必须完整可粘贴
4. 依赖真机环境的条目（多显示器、系统通知、打包），单独标 `[环境依赖]`，跑不了不算缺陷
