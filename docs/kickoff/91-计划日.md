## 一、问题与定性

用户要给长期计划排每天内容（考试、训练、课程表这类），现在只能一条条建，建成之后**全部堆在任务栏**。

代码现状取证，两个直接原因：

1. `src/renderer/main/features/tasks/tasksModel.ts` 的 `groupTasks` 里，`byType` 只要 `status` 是 `todo` / `doing` / `pending_review` / `reviewing` 就进列表，**完全不看日期**。所以下个月的任务和今天的任务在同一屏。
2. `dueAt` 一个字段被当两件事用：「我打算哪天做」和「最晚哪天交」。所以没法表达「这件事我下周三做，但月底才交」。

`daily` + `repeatRule` 只能表达「每天做同一件事」，表达不了「每天做不一样的事」，所以长期计划必须落成多条独立任务——那正需要「哪天该出现」这个维度。

## 二、规格

### 2.1 数据库迁移（新增第 10 版）

新建 `src/main/db/migrations/010_task_planned_day.sql`，全文只有一行：

```
ALTER TABLE tasks ADD COLUMN planned_day TEXT;
```

`src/main/db/migrations/index.ts`：照 `009` 的写法 import（变量名 `taskPlannedDaySql`），`MIGRATIONS` 数组末尾追加 `{ version: 10, name: '010_task_planned_day', sql: taskPlannedDaySql }`。

迁移**不回填数据**（本项目铁律：迁移不写业务数据）。所有历史任务的 `planned_day` 为 `NULL`，行为与现在完全一致。

### 2.2 共享判断模块（新建 `src/shared/planDay.ts`）

零依赖模块，不引 react / electron / db / 客户端时间，导出两个函数：

- `isValidPlanDay(s: string): boolean`
  - 先过 `^\d{4}-\d{2}-\d{2}$`；
  - **必须再验是真日历日**：用 `Date.UTC` 构造后回读年 / 月 / 日是否与原文一致，`2026-02-30`、`2026-13-01` 必须判假。只靠正则是不合格的。
- `visibleOn(plannedDay: string | null, today: string): boolean`
  - `plannedDay === null || plannedDay <= today`
  - 两边都是 `YYYY-MM-DD`，字符串字典序即日期序；**不要**转 `Date` 再比，避免时区把日界带偏。

文件头注释写明：`plannedDay` 是「打算哪天做」，`dueAt` 是「最晚哪天交」，两者互相独立，可以早于、晚于或不存在。

### 2.3 领域类型（`src/shared/types/domain.ts`）

- `Task` 在 `dueAt` **之前**加 `plannedDay: string | null`。注释：010 迁移加的列，本地日历日 `YYYY-MM-DD`；「打算哪天做」；`null` = 没有计划日、立刻可见；`daily` 恒为 `null`。
- `TaskPatch` 加 `plannedDay?: string | null`。
- `TaskDraft` 在 `dueHint` **之后**加 `plannedDay: string | null`，注释：AI 识别出的「打算哪天做」，识别不出来就是 `null`，确认落库时原样带下去。

### 2.4 映射层（`src/main/db/mappers.ts`）

- `TaskRow` 加 `planned_day: string | null`（注释：010 迁移，老行为 NULL）；
- `TASK_COLUMNS` 与 `TASK_INSERT_COLUMNS` **两个数组都要**在**末尾**追加 `'planned_day'`；
- `mapTask` 返回值加 `plannedDay: row.planned_day`；
- `taskInsertParams` 返回数组**末尾**追加 `t.plannedDay ?? null`；
- `TaskInsert` 加可选 `plannedDay?: string | null`。

插入语句是按这两个数组逐位拼的，多一个少一个都会炸，改完自己数一遍两边长度是否相等。

### 2.5 仓库层（`src/main/db/repositories/taskRepo.ts`）

`patch()` 的列拼装加一条：`plannedDay !== undefined` 时写 `cols.planned_day`。`null` 也要照写（只有 `undefined` 才跳过）。

### 2.6 业务层（`src/main/services/taskService.ts`）

- `TaskCreateInput` 加 `plannedDay?: string | null`；
- 新增一个私有归一函数（名字自取，语义如下），创建与修改两条路径都过它：

1. `raw == null` → 返回 `null`；
2. `type === 'daily'` 且 `raw !== null` → 抛 `appError('INVALID_INPUT', '每日任务不需要计划日')`；
3. `!isValidPlanDay(raw)` → 抛 `appError('INVALID_INPUT', '计划日必须是 YYYY-MM-DD')`；
4. 否则原样返回。

- `createTask` 在拼 insert 时调它；`updateTask` 只有在 `patch.plannedDay !== undefined` 时才调，结果写回 patch。

### 2.7 列表过滤（本单核心，`src/renderer/main/features/tasks/tasksModel.ts`）

`groupTasks` 里 `byType` 的**活跃段**（即 `status !== 'done' && status !== 'missed'` 那个 filter）追加条件 `&& visibleOn(t.plannedDay, today)`。

**「今日已完成 / 今日已错过」那一段不要加这个条件**——用户今天做完了就要看得见，哪怕它的计划日在未来。

注释写清三件事：计划日在未来的任务不进列表；昨天没做完的因为 `plannedDay <= today` 会**自动**继续出现；**严禁**写任何「滚动到今天」「顺延搬运」的逻辑，本单不做这件事，别自作主张。

### 2.8 晨报口径（`src/main/services/chatBrief.ts`）

`buildTodayBrief` 里 `const pending = input.tasks` 改成先按同一个 `visibleOn` 过滤（`today` 用函数里已经算好的那个本地日）。

这是硬要求：不过滤的话，一份 30 天的计划会让晨报变成「待办 30 条」，而实际上今天只有一条。

`overdue` 统计、`doneToday`、昨天那行**都不动**。

### 2.9 AI 识别

1. `src/main/ai/schema.ts` 的 `parsedTaskSchema` 加字段：
   `planned_day: z.string().regex(/^\d{4}-\d{2}-\d{2}$/).nullable().optional()`
   `.optional()` 是刻意的：既有 fewshot 样例没有这个键，缺省不能被判无效输出。
2. `src/main/ai/pipelines/parse.ts` 的 `toTaskDrafts` 每一条加 `plannedDay: task.planned_day ?? null`。
3. `src/main/ai/prompts/parse.system.md` 增加一节「计划日 `planned_day`」，规则只三条：
   - 只有用户**明确说了**某件事打算哪天做（"周三做""下周一再说"）才填，填 `YYYY-MM-DD`；
   - 任务的截止日期**不等于**计划日，`due_hint` 是「最晚哪天交」，`planned_day` 是「打算哪天做」，**不要把 due_hint 的日期复制过去**；
   - 拿不准就填 `null`。
   **本节不许教模型怎么拆多天计划**（那是下一单），也不许改「一次最多 10 个任务」那节。
4. `src/renderer/main/features/chat/useChatData.ts` 的 `promotePatchOf(draft)` 要把 `plannedDay: draft.plannedDay` 带进 patch，否则草稿确认后就丢了。
