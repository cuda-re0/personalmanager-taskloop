# 代码审核开工词（可复用，每轮审核发一次）

> **这不是走形式。** 审核方要能对着文档条款指出"你违反了哪一条"，否则它会给你一堆"建议用箭头函数"这种废话。

## 第一步：先看标准，再看代码

**不要先读代码再"感觉"哪里不对。** 先按下面的顺序把标准读一遍，建立判断依据：

| 你要判断什么 | 标准在哪 |
|---|---|
| 类型 / IPC 方法 / 事件 / 积分公式 | `docs/02-CONTRACTS.md` §1、§2、§3、§4、§5 |
| 表结构、索引、状态机、统计口径、时区处理 | `docs/01-DATA-MODEL.md` 全文（重点 §2、§3、§4、§4.1） |
| AI 调用、prompt 约束、JSON 校验、证据闸门 | `docs/03-AI-CONTRACT.md` §3、§4、§6 |
| 界面规格、设计 token、文案纪律 | `docs/04-UI-SPEC.md` §1–§7 |
| 这个模块该改哪些目录、禁令是什么 | `docs/05-BACKLOG.md` 对应 `W` 段 + 末尾「协作纪律」 |
| 哪些是用户明确要求、不许推翻 | `docs/00-ARCHITECTURE.md` §1 需求溯源表 |
| 这个模块的开工词（它当时被要求做什么） | `docs/kickoff/` 对应文件 |

**审核结论必须引用条款。** 每条问题后面写清"违反 `02-CONTRACTS.md` §5 的 `computePlannedPoints` 签名"，而不是"建议改成……"。

## 第二步：不要相信被审方的话，自己跑

逐条自己执行，把输出贴进报告：

```
npm run typecheck     # 必须零错误
npm run lint          # 必须零错误零警告
npm test              # 有测试的模块必须全绿；没有测试就是 P1 问题
git diff --stat a9c86c7..HEAD    # 看改了哪些文件
```

**然后做一件它可能不会主动说的事**：把 `git diff --stat` 里的文件列表，和开工词里的「你能改的目录」逐条比对。**改了不属于自己的目录 = P0**，不管改得多好。

**并行施工时，口径一律按提交判，不按 HEAD 判。** v0.25 起多个施工方共用一个工作区，`git diff --stat <起点> HEAD -- <目录>` 会把别人的提交算进来，于是「主进程零改动」这类口径天天误红。判法改成：

```
git show --stat <他的提交>          # 他到底改了什么，这才是判定依据
git diff --stat <起点> <他的提交> -- <目录>   # 需要区间时，终点用他的提交
```

自己工作区干净（`git status --porcelain` 空）是另一件事，单独判。

## 第三步：按这六个维度审，按级别报

### P0 · 阻断（必须打回，修完才能合并）

1. **改了 `src/shared/**`** —— 类型、`channels.ts`、`rubric.ts`。这是 6 个模块唯一的公共语言，任何改动都会让其他模块对不上。
2. **擅自改契约**：给类型加字段、把 `null` 改成 `undefined`、改方法签名、改事件名。
3. **越界改文件**：改了不属于本模块的目录（见第二步）。
4. **数据正确性错误**：三条条件唯一索引写错（尤其 `uq_ledger_task_done` 漏了 `AND occurrence_id IS NULL`）、`day` 字段用 `date('now')` 算、跨表写入没走事务。
5. **绕过硬约束**：`taskService.complete` 里没有证据校验、积分公式被复制成第二份、模型输出被当作分数直接用。

### P1 · 严重（改完再合并）

6. **违反开工词的禁令**：渲染层出现 `require('electron')`、handler 里直接写 SQL、引入了 UI 框架、prompt 里出现具体分值、`dangerouslySetInnerHTML` 直出。
7. **安全**：API Key / token 出现在代码、日志、被 git 跟踪的文件里。
8. **错误处理缺陷**：handler 把异常抛到 IPC 外面、AI 失败导致白屏、外部渠道失败拖垮整条提醒。
9. **该有测试却没有**：数据层的唯一索引、时区、幂等生成这几条，没有自动化测试就是 P1。

### P2 · 质量（可以下一轮修）

10. 重复代码、命名与文档不一致、注释与实现不符。
11. 顺手做了没要求的功能（这也是问题：没要求的代码没人负责维护）。

**不要报的东西**：代码风格偏好（箭头函数 vs function、要不要拆文件）、"建议引入某库"、性能微优化（除非有实测数据）。这些不算问题，报了只会稀释重点。

## 禁止

- 不许改任何代码。发现问题只报告，不动手（你动手，被审方就不知道错在哪，下轮还会犯）
- 不许给"整体不错，建议优化"这种结论。要么列出具体条目，要么写"未发现问题"
- 不许把风格偏好当问题报
- 不许只读被审方的自检表就下结论，必须自己跑命令
- 不许在报告里写"可能""也许"。不确定的，写"无法判断，原因：xxx"

## 使用者注意（给我自己看的）

1. **每轮审核前必须先 commit。** 没有基线提交，`git diff` 是空的，审核方只能看到最终代码，看不到"改了什么"，越界改动就查不出来。
2. 审核范围不要一次给太多模块。一轮审 2-3 个模块，报告才有用；6 个一起审，它会开始概括性总结。
3. 审核方报告里的 P0 修完，**要重新审一次**（只审 P0 涉及的文件），不要直接信"已修复"。

## 施工方硬约束（实战踩出来的，写进每单开工词）

1. **tests 不得 import 任何用到 `window` 的渲染模块**（2026-10-29 `66a9664` 踩出）：
   `tsconfig.test.json` 没有 DOM lib，`useCalendarData`/`useTasksData` 这类 hook 一被测试
   import 就挂 typecheck。纯逻辑放纯函数文件测；组件行为用源码结构断言（`calendarPanelWiring` 是范例）。
2. **并行施工尽早分段提交**（2026-10-29 两起事故）：未提交的实现被并行会话的工作区重置吞掉过
   两次（W6 v0.26、W6B 第一轮），均靠会话记录重放恢复。每完成一个文件就 `git add`，
   逻辑段落完成就分段 commit（message 带 WIP 前缀也行），不要攒到全部完工一次提交。
3. **起真机实例先核对身份**（见 `17 §3.1`）：临时库应为空；页面却有任务 = 连到别人的窗口，立刻停。
