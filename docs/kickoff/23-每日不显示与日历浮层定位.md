## 问题 1：新建「每日」任务后，右栏 ① 里看不到它

### 根因（已核实）

1. 每日组只渲染**今天且 `pending` 的 occurrence**：
   `features/tasks/tasksModel.ts:48` `occurrences.filter(o => o.status === 'pending' && o.day === today)`。
   daily 任务不进「限时 / 活动」两组（`topLevel.filter(t => t.type === 'deadline' | 'event')`），
   所以**没有今天的 occurrence = 界面上根本不存在这个任务**。
2. 手动建任务的链路没有补 occurrence：`ipc/registry.ts:283` 的 `CH.task.createManual`
   只调 `taskService.createTask()` 然后广播 `task.created` + `daystats.changed`。
   `createTask()` 本身不建 occurrence；`ensureRange` 只在 `promoteDraft` 里被调（`taskService.ts:464`）。
3. 渲染层也不会自愈：`useTasksData.ts:129` 的 `task.created` 只 `reloadTasks()`，
   不重拉 occurrence。于是状态里永远没有这一行。

结果：用户建了每日任务，列表里什么都没有；要等到他**打开日历**（`occurrence.listByRange`
内部会 `ensureRange`）才被补出来，看起来像"建了但丢了"。

### 怎么改

**A. 主进程：建每日任务时补今天的 occurrence（根因修）**

- 在 `taskService.ts` 新增一个函数（名字自取，如 `createManualTask`），内部：
  `createTask(input)` → 若 `input.type === 'daily'` 则 `occurrenceService.ensureRange(today, today)`。
  **只补今天，不要补到今天+3**：用户此刻要看到的是今天这一行，未来几天的行由
  `occurrence.today` / `listByRange` 按需补（`OCCURRENCE_HORIZON_MONTHS` 那套机制不动）。
- `createTask` 函数体**一个字不许改**（`promoteDraft` 依赖它，且它自己已经 ensure 过了）。
- `ipc/registry.ts` 的 `CH.task.createManual` 改成调新函数；广播顺序：
  `task.created` → `occurrence.created`（**只带今天这一条**，没有新建就不发）→ `daystats.changed`。
  只推今天是硬要求，`registry.ts:165` 那条注释解释过原因（未来日期会让所有每日任务提前出现多行）。

**B. 渲染层：`task.created` 也重拉 occurrence（兜底，防同类复发）**

- `useTasksData.ts` 的事件 switch 里，`task.created` 分支在 `reloadTasks()` 之外再调一次
  `reloadOccurrences()`。`task.updated` / `task.removed` **不要**加（每次改任务都多打一次 IPC，没必要）。
- 理由：任何"建 daily 的入口"漏了补行，界面都能自愈一次，不必逐个入口打补丁。

### 验收

- 建一条每日任务 → 立刻出现在「每日」组，圆形勾选框可点，标题正确。
- 建一条限时 / 活动任务 → 不产生任何 occurrence 行。
- 建每日任务后**不打开日历**，直接看列表 → 有。
- 连续建 3 条每日任务 → 3 行，不多不少（不能因为重复 ensure 出双行）。

## 问题 2：点日历里的日期，展开框跑到整个面板的最底部

### 根因（已核实）

`calendar.css:129`：

```css
.calendar-floor {
  position: absolute;
  top: 100%;      /* ← 相对 .calendar-panel（240px）的底部，不是相对被点的格子 */
  left: 0; right: 0;
}
```

`.calendar-panel` 是 `position: relative` 且固定 `height: 240px`，所以 `top: 100%` 等于
**日历块的下边缘**。于是不管点的是 1 号还是 31 号、哪个月，浮层都出现在日历块正下方、
压在 ③ 积分区上——用户看到的就是"框直接跑到最底部"。这是定位基准选错，不是 z-index 问题。

### 怎么改

浮层改成**以被点格子的那一行为锚**，贴着这一行的下边缘展开；下方空间不够就翻到这一行**上方**。

具体（照这个做）：

1. 点格子时记下它的 `offsetTop` 与 `offsetHeight`（`e.currentTarget` 即可；
   `.calendar-grid` 不是 positioned，所以 `offsetParent` 就是 `.calendar-panel`，数字可直接用）。
   存进组件 state，**不要**每次渲染去 `querySelector` 量 DOM。
2. 浮层用**内联 `top`**，删掉 CSS 里的 `top: 100%`：
   - 行底 `rowBottom = cellTop + cellHeight`
   - 期望位置 `top = rowBottom + 2`
   - 浮层实际高度 `h`（渲染后量一次；首帧没有值时按 `max-height` 估）
   - 若 `top + h > 面板高度 - 8` → 翻到上方：`top = cellTop - h - 2`；仍 `< 0` 就取 `0`
3. 水平不变：`left: 16px; right: 16px`（与 `.calendar-grid` 的 `padding: 2px 16px 0` 对齐）。
4. `max-height: 200px` 保留，列表内部滚动；`z-index` 保留 20。
5. 关闭逻辑（点外部 / `×`）**不改**。
6. `.calendar-panel` 的 `height: 240px` 不许改——浮层本来就该溢出面板、压在 ③ 上面，这是设计。

### 验收

- 点月初第一行（如 1 号）→ 浮层紧贴那一行下方，不跑到面板底部。
- 点月末最后一行 → 浮层翻到该行**上方**，整块仍在窗口内、不被裁。
- 点中间任意一行 → 浮层出现在该行下方（若下方空间不足则上方）。
- 换到 9 月 / 11 月，按三种位置各点一次 → 行为一致（"每周每月一样"要变成"每周每月都贴着自己那一行"）。
- 浮层压在 ③ 积分块**之上**，不被遮挡、不透明穿透。
- 浮层里点任务行 → 仍然跳回 ① 并高亮（原行为不许坏）。
