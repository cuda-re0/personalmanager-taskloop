## 交付

### 1. `connection.ts`

单例连接。启动时依次执行：

```ts
db.pragma('journal_mode = WAL')
db.pragma('synchronous = NORMAL')
db.pragma('foreign_keys = ON')
db.pragma('busy_timeout = 5000')
```

`migrate()` 用 `PRAGMA user_version` 记录已应用版本（**权威**），顺序执行未应用的迁移文件。`schema_meta` 只写迁移历史明细，不参与版本判定——细则见 `01-DATA-MODEL.md` §5。

### 2. `migrations/001_init.sql`

`docs/01-DATA-MODEL.md` 全部建表语句、索引、唯一索引，**一字不改地抄**。

**重点：这里有 3 条索引是最容易写错的地方，必须逐字对照文档。**

```sql
-- 限时/活动：一个任务只准发一次完成分
CREATE UNIQUE INDEX uq_ledger_task_done
  ON point_ledger(task_id)
  WHERE reason_code = 'task_done' AND occurrence_id IS NULL;

-- 每日任务：同一天只准发一次分（不同天各自发）
CREATE UNIQUE INDEX uq_ledger_occurrence
  ON point_ledger(occurrence_id)
  WHERE occurrence_id IS NOT NULL;

-- 每日任务：同一任务同一天只能有一条 occurrence
CREATE UNIQUE INDEX uq_occurrence_task_day
  ON task_occurrences(task_id, day);
```

第一条如果漏了 `AND occurrence_id IS NULL`，每日任务第 2 天的发分会被直接拒掉。这是本期第一号坑。

### 3. `repositories/`

`taskRepo`、`occurrenceRepo`、`messageRepo`、`ledgerRepo`、`reminderRepo`、`statsRepo`、`settingRepo`。

规则：

- 全部**同步**方法（better-sqlite3 是同步的，不要包 Promise）
- 入参出参用 `@shared/types/domain` 的类型
- `snake_case` ↔ `camelCase` 的映射**只写在一处**（做一个 `mapTask(row)` 之类的函数，不要在每个方法里手写）
- `null` 与 `undefined` 不许互换（DB 里 `NULL` 一律映射成 `null`）

### 4. `occurrenceService.ensureRange(from, to)`

按 `01-DATA-MODEL.md` §2.1.3 的规则幂等生成每日任务的 occurrence。

三条硬约束：

- 只生成 `from` 到今天（**不生成过去日期**）
- 不生成 `active_to` 之后的日期
- 连续调用 N 次，数量不增长（靠 `uq_occurrence_task_day` + `INSERT OR IGNORE` 保证）

### 5. 事务封装

`tx(fn)`，透传 `db.transaction`。**所有跨表写入必须走 `tx`**：写 ledger + 更新 task + upsert daily_stats 是三张表，不在一个事务里就会对不上账。

### 6. 状态机校验 `assertTransition(type, from, to)`

非法跳转抛 `AppError{ code: 'CONFLICT' }`。

注意：`daily` 类型**不接受** `reviewing` / `done`（每日任务走 occurrence，不走任务状态机）。这条容易漏。

### 7. `rebuildDailyStats()`

从 `point_ledger` + `tasks` 全量重算 `daily_stats`。用于兜底和验证。

## 验收（**写成自动化测试，不是手工点一遍**）

用 vitest 或 node:test，跑 `npm test` 必须全绿：

- [ ] 建库 → 建任务 → 查任务，字段全等（含 `type`、`repeatRule`、`reminderOffsets`、`requiresEvidence`）
- [ ] `todo → done` 直跳被拒（`CONFLICT`）
- [ ] `todo → doing → reviewing → done` 通过
- [ ] `daily` 任务走 `reviewing` 被拒
- [ ] 同一限时任务插两条 `task_done` 流水 → 第二条被 `uq_ledger_task_done` 拒
- [ ] **同一每日任务连续两天各发一次分 → 两次都成功**（这条必须单独写一个测试，最容易挂）
- [ ] 同一每日任务同一天发两次分 → 第二次被 `uq_ledger_occurrence` 拒
- [ ] `ensureRange` 连续调用 3 次，occurrence 数量不增长
- [ ] `ensureRange` 不生成过去日期、不生成 `active_to` 之后的日期
- [ ] 删父任务 → 子任务级联删除、`task_occurrences` 级联删除、`point_ledger.task_id` 变 `NULL`（流水不删）
- [ ] 1000 任务 + 5000 流水 + 3000 occurrence 下，`task.list`、`calendar.dayIndex`、`points.monthStats` 各 < 20ms
- [ ] **东八区 00:30 写入，`day` 落在当天而不是前一天**（用 `TZ=Asia/Shanghai` 跑这个测试；不许用 SQLite 的 `date()` 处理 UTC 字段）
