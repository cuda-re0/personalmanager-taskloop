## 为什么要这一单（事实，不要扩写）

架构方在本机用 Electron 网络栈实测（sha 固化的同一批 15 个文件）：

- 冷缓存：`out/manifest.json` **11,173 ms**、`renderer/assets/notify-*.js` **12,180 ms**、`main-*.js` 5,081 ms
- 同一批文件**第二次请求全部 1~8 ms**（CDN 已热）
- 另有一次单文件请求直接抛 `net::ERR_HTTP2_PROTOCOL_ERROR`

现状 `repoSource.ts` 的 `TIMEOUT_MS = 10_000` **且一次都不重试**。后果有两个，都是真的：

1. 冷缓存下第一次拉新版本，manifest 或某个大文件会在 10 秒被自己 abort，整单失败。
2. 失败后 `updateService` 会写 `attemptedVersion` 标记，**自动检查在 24 小时内不再试这个版本**（`ATTEMPT_TTL_MS`）。用户表现为「明明发了新版，机器一天都不动」。

所以这一单只做两件事：**超时放宽到 20 秒**、**可重试的失败自动重试**。不改任何业务语义、不改覆盖与回滚。

## 一、常量

`src/main/update/repoSource.ts`：

- `TIMEOUT_MS` 由 `10_000` 改成 `20_000`（注释写清：实测冷缓存 11~12 秒，10 秒会自杀）
- 新增 `const MAX_ATTEMPTS = 3`（含首次，即最多重试 2 次）
- 新增 `const RETRY_DELAY_MS = 500`（每次重试前等 500 ms × 已重试次数，即 500 / 1000）
- 新增 `const TOTAL_BUDGET_MS = 5 * 60 * 1000`（`downloadRepoTree` 整体预算，见第四节）

## 二、重试助手

新增**不导出**的两个内部函数：

**1）`nonRetryable(err, failure?)`** —— 给错误打「不许重试」标记后原样返回

- 若传了 `failure`，内部复用现有 `withFailure(err, failure)`
- 无论走哪条，都要 `Object.assign(err, { retryable: false })`
- 用途：404、4xx、解析/校验失败、超限、路径越界、版本不一致 —— 这些重试一万次也是同样结果

**2）`withRetry(fn: () => Promise<T>, label: string): Promise<T>`**

语义（严格按此，不要自由发挥）：

- 最多执行 `MAX_ATTEMPTS` 次
- 成功即返回
- 捕获的错误若 `err.retryable === false` → **立即抛出**，不重试
- 否则（网络错误、`AbortError` 超时、5xx）：
  - 若还有次数：`console.warn('[update] ' + label + ' 第 N 次失败，Xms 后重试：' + message)`，`await` 一个 `RETRY_DELAY_MS * N` 的 `setTimeout`，再试
  - 次数用尽：抛出**最后一次**的错误
- `label` 只用于日志，四处的取值分别是 `'取 commit sha'`、`'取清单'`、`'下载 ' + rel`、`'取 package.json'`

**重要**：`fn` 内部**继续保留它自己的 `AbortController` + `setTimeout`**（即每次尝试都是独立的新控制器与新计时器）。不要为了重试把控制器提到外面复用——那样第二次尝试会带着已 abort 的信号，永远失败。

## 三、四处请求接入 `withRetry`

把现有四个请求段的**整个函数体**（含 `res.arrayBuffer()` / `res.text()` 读取）包进 `withRetry`，`fn` 内部结构一个字不改：

1. `fetchRepoHead` 的请求段
2. `fetchRepoManifest` 的请求段
3. `downloadRepoTree` 里**每个文件**的下载段（`label` 带 `rel`）
4. `downloadRepoTree` 里 `package.json` 的请求段

**哪些错误要标 `nonRetryable`**（必须逐个落实，不要漏）：

- 三处的 `404`（现已 `withFailure(..., 'notfound')`）→ 改成 `nonRetryable(..., 'notfound')`
- `!res.ok` 且 `res.status < 500`（4xx，含 403 限流）→ `nonRetryable(..., 'http')`；`>= 500` 保持可重试
- `fetchRepoManifest` 里清单解析/校验/超 1 MiB 的整段 `catch`（现在统一 `withFailure(e, 'shape')`）→ 改成 `nonRetryable(e, 'shape')`
- `fetchRepoHead` 里 `res.json()` 失败与 sha 形状不对 → `nonRetryable(..., 'shape')`
- `downloadRepoTree` 里：单文件超 8 MiB、内容为空、总量超 32 MiB、路径越界后的跳过（跳过不是错误，保持现状）
- `downloadRepoTree` 末尾的「`package.json` 版本与清单不一致」→ `nonRetryable`（它本来就在 `withRetry` 之外，只需打标记不影响语义，也可不动；但**不要**把这条校验移进重试范围）

**不许改**：`parseRepoManifest` 的任何校验规则、`refOf`、`REQUIRED_FILES`、staging 结构与路径安全校验、写完 `package.json` 后的版本比对逻辑。

## 四、整体预算

`downloadRepoTree` 开头记 `const startedAt = Date.now()`；在**每个文件开始前**检查：若 `Date.now() - startedAt > TOTAL_BUDGET_MS`，抛 `new Error('仓库源下载超时：已用超过 5 分钟')`（不重试）。

目的：文件多 + 网络差时不要无限拖（15 个文件 × 3 次 × 20 秒理论上能拖很久）。`package.json` 那一步不受预算限制，照常执行。
