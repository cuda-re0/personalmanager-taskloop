## 2. 七条硬性口径（都是实测踩出来的，不是风格偏好）

### 2.1 每次请求必须注入当前时间

`due_hint` 恒为 `null` 的根因：模型不知道"明天"是哪天。system 消息末尾固定追加（格式已定，别自创）：

```
【当前时间】2026-10-29 星期四 10:52（Asia/Shanghai）
解析"明天/下周三/三小时后"这类相对时间时，一律以此为准，并换算成带时区的 ISO8601。
```

日期与星期用 `src/shared/localDay.ts` 算（`todayLocalDay()` + 一次 `Intl.DateTimeFormat` 取星期），**禁止 `toISOString().slice(0,10)`**（那是 UTC 日，东八区凌晨会差一天）。按小时缓存，别每条消息重算。

**注入后仍然 `due_hint: null` 才算模型能力问题**——那种情况在交付报告里写明，不要自己加正则去猜日期。

### 2.2 `max_tokens: 2048`，`finish_reason` 必查

`length` → `AI_PARSE_FAILED`，`retryable: true`，**不重试**（同样的 token 预算会同样被截断）。

### 2.3 超时 60s，且必须可中断

`AbortController` 由 `aiService` 持有。应用退出 / 用户点取消 → `abort()`。`AbortError` 不算失败，**不落 error 气泡**，把占位消息标成 `status: 'aborted'`（`MessageStatus` 已有枚举，用现成的）。

### 2.4 strip 围栏 + zod 双重兜底

```
原始 content
  → trim
  → 若以 ``` 开头：剥掉首行栅栏与尾行栅栏（正则只认 ```json / ``` 两种）
  → JSON.parse（失败 → 第一次重试，把 parse 错误拼进 user 消息让它自修）
  → schema.safeParse（失败 → 第二次也是最后一次重试，把 zod 的 issues 拼进去）
  → 仍失败 → AI_PARSE_FAILED
```

**重试总共只 1 次**（`maxRetries: 1`），不是"parse 一次 + zod 一次"各一次。

### 2.5 推理 token 要计入 `tokens_out`

上游把 `reasoning_tokens` 算进 `completion_tokens`。写回 `messages.tokens_out` 时用 `usage.completion_tokens`，不要自己数 `content.length`。

### 2.6 `intent` 会被照抄成枚举占位符

实测 `glm-4-flash` 直接输出 `"create_task|review_task"`。zod `z.enum([...])` 会拒，走 2.4 的重试。重试后仍错 → `AI_PARSE_FAILED`。**不许写容错分支去 split('|') 猜一个**——那是把模型的错误变成数据的错误。

### 2.7 `type × difficulty` 越界要拒绝，不归位

`ALLOWED_DIFFICULTIES`（`src/shared/taskRules.ts`）约束：`daily → trivial/easy/medium`、`deadline → easy/medium/hard`、`event → medium/hard/epic`。zod 里 `refine`，**不许静默改成合法值**（`03 §4.1`）。

### 4.2 `src/main/ai/glmClient.ts`

- `https://open.bigmodel.cn/api/paas/v4/chat/completions`
- 模型取 `settings['ai.provider'].model`（默认 `glm-5.3-flash`）
- 按本文 §2.2 / §2.3 / §2.4 实现
- **收到 `content` 为空串且 `finish_reason === 'length'`** → `AI_PARSE_FAILED`，`detail` 写 `finish_reason=length`（这是给人排查用的，不是给 UI 的）
- HTTP 状态映射：`401/403 → AI_NOT_CONFIGURED`、`429 → AI_RATE_LIMITED`、`5xx / 网络错 → AI_UPSTREAM_ERROR`（`retryable: true`）
- **`detail` 里不许出现 key 片段**，`console.*` 同样

### 4.3 `src/main/ai/config.ts`（新增，本版必须）

key 的读取按 `03 §9.7` 的三级优先级。实现要点：

- `safeStorage` 分支：`userData/ai-key.bin`，`isEncryptionAvailable()` 为 false 时降级到环境变量并 `console.warn` 一次（**不打 key**）
- 环境变量分支：`process.env.ZHIPU_API_KEY`；`!app.isPackaged` 时才额外读仓库根的 `.env.local`（自己解析 `KEY=VALUE`，别引新依赖）
- 导出 `readKey(): string | null` 与 `writeKey(key: string): void`。**`writeKey` 不许注册成 IPC**（04 没有设置页，加了没人调）

### 4.4 `src/main/ai/schema.ts`

`ParseResultSchema` / `ReviewResultSchema`，字段严格对齐 `03 §4.1` / `03 §4.2`。

- **`.strict()` 或显式剥多余键**：模型多给的字段不许进业务层
- `verdict` 允许 `pass | partial | fail | need_evidence`
- `quality` / `result` 允许 `null`
- `type × difficulty` 的 `refine`（§2.7）
- `confidence` 0~1
- `due_hint` / `daily_time_hint` 允许 `null`；**`due_hint` 非 null 时必须是可被 `new Date()` 解析的 ISO8601**，否则算无效输出走重试

### 4.5 `src/main/ai/prompts/`

```
system.base.md      人格、语言、铁律（中文输出、不臆造、不输出分数）
parse.system.md     03 §4.1 全部硬约束（含 type 判定表、requires_evidence 表）
review.system.md    03 §4.2 全部判定标准
parse.fewshot.json  4 组正例：单任务 / 图转任务 / 多任务 / 纯闲聊
```

- **prompt 里绝对不许出现具体分值**（写"这个值 20 分"模型会照抄，积分体系就废了）
- `parse.fewshot.json` 里**必须有一条 event 正例**（考试/面试/答辩），实测模型会把"下周三考英语六级"判成 `deadline`
- 每组 prompt 首行写版本注释 `<!-- v1 2026-10-29 -->`

### 4.6 `src/main/ai/pipelines/parse.ts`

消息（文本 + 图片）→ 多模态 payload → `ParseResult` → `TaskDraft[]`。

补齐三样（`03 §4.1` 末段）：

- `localId = nanoid(8)`
- `pointsPlanned`：`daily → cfg.dailyBase`；`deadline/event → computePlannedPoints(difficulty, cfg)`。**`cfg` 必须传 `bootstrap.settings` 里的完整 `PointsConfig`，不许省参数落回 `DEFAULT_CONFIG`**（`02 §5.2` 有明条）
- `reminderOffsets`：`deadline → [-1440, -60]`、`event → [-10080, -4320, -1440]`、`daily → []`

图片：调 `attachmentService.read(id)` 取 `{ bytes, mime }`，转 base64 data URL。**单次最多 4 张**；超出的丢掉并在 `reply` 里说明（不要报错）。

### 4.7 `src/main/ai/pipelines/review.ts`

- **硬闸门先行**：`requiresEvidence === true && evidence.length === 0` → 直接返回 `{ verdict: 'need_evidence', … }`，**不调模型**。日志里要能看出"这次没发请求"。
- `type === 'event'` → `result` 必填、`quality` 恒 `'met'`；其他类型 `result` 必须 `null`
- `reason` ≤50 字、`followup` ≤40 字

### 4.8 `src/main/services/aiService.ts`

六个入口，全部**不 throw 到 IPC 外面**：

| 函数 | 行为 |
|---|---|
| `send({ text, attachmentIds })` | 写 user 消息 → 广播 `message.appended` → **立刻返回** `{ userMessage, assistantMessageId }` → `void` 后台跑一轮 → 结果广播 `message.patch` + `ai.status('idle')` |
| `retry({ messageId })` | 找到失败那轮的 user 文本重跑，同一条 assistant 消息原地 patch |
| `confirmDraft({ messageId, localId })` | 转调 `taskService.promoteDraft`（**不要复制一份逻辑**） |
| `rejectDrafts({ messageId, localIds })` | 从 `meta.drafts` 里移除，patch 消息；空了就把 `kind` 改成 `text` 并清 `meta` |
| `review({ taskId, userText })` | 读任务 + `evidence` → `pipelines/review` → 落一条 `kind='task_review'` 消息 → 返回 `ReviewVerdict` |
| `health()` | `{ configured, model, multimodal }`；`multimodal` 靠**一次真实带图调用**探测并按进程缓存 |

**`send` 必须秒返回**：`03` 与 `02 §3.3` 都写了"渲染层不要 await 到 AI 完成"。AI 那段是 `void runTurn()`，任何异常在 `runTurn` 内部收口成一条 `kind='error'` 消息（`retryable: true`）。

`ai.status` 广播时序：`thinking` → （可选 `streaming`）→ `idle`。**失败也要发 `idle`**，否则 UI 转圈永远不停。

### 4.9 `scripts/verify-ai.mjs`

- 默认跑全量 3 项（纯文本 / 带图 / usage），`--quick` 只跑纯文本
- key 从 `process.env.ZHIPU_API_KEY` 读（**不读 `.env.local` 里的值打印出来**）
- 输出：模型名、是否吃图、耗时、`usage` 全字段、`finish_reason`
- **不打印 key，不打印完整响应体**（截断到 200 字符）

### 4.10 `docs/verify-ai-result.md`

模型名、三项验证结果、单次 token 与耗时、你在复核时观察到的与 `03 §9` 的任何**不一致**。
