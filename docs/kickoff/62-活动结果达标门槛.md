## §0 用户裁决与现状

**用户裁决（2026-11-03）：**

- 考试：及格以上才算完成、才发积分；**及格以下算任务失败**。
- 比赛：拿到奖项才算完成；**否则失败**。
- **不加活动子类型字段**，靠任务描述表达是哪一类。
- **达标标准全交给模型判断**（描述里写了就按描述，没写就按常识）。

**现状（已核实，不要重新调研）：**

- `EventResult = 'exceeded' | 'met' | 'below'`，系数 `1.2 / 1.0 / 0.85`（`src/shared/points/rubric.ts`）。
- AI 审核已经会产出它（`review.system.md` 有对照表，`toVerdict` 已透传）。
- **问题**：模型判「结果不理想」时返回 `pass + result: 'below'`，任务照样走 `complete`，只打 0.85 折。等于考 30 分也能完成、还拿走 85% 的分。
- **第二个问题**：`decideReview` 只在「已超期」时才判 `missed`。活动任务的结果判定不该看超期。

**要做到用户要的，必须四层一起改**（每层职责不同，不是重复）：

| 层 | 位置 | 职责 |
|---|---|---|
| 1 | `review.system.md` | 告诉模型：不达标就是 `fail`，不是 `pass + below` |
| 2 | `toVerdict` | 模型抽风返回 `pass + below` 时强制成 `fail` |
| 3 | `completeTask` | 任何入口想让 `below` 计分都拒绝（兜底） |
| 4 | `decideReview` | 活动的 `fail` 无条件判 `missed`，不看超期 |

**明确不做（越界即返工）：**

- 不加 `eventKind` / `eventResultRule` 之类的字段，**不做数据库迁移**。
- 不改 `EventResult` 的值域（`exceeded` / `met` / `below` 三个值保留）。
- 不改 `stateMachine.ts`（`reviewing → missed` 这条边已存在）。
- 不加任何界面文案、不加输入框、不加提示。
- 不做「失败后重考」的复活路径（`missed` 仍是终点，只有归档一条出口）。

## §1 第一层：prompt 改造

`src/main/ai/prompts/review.system.md`，把 `# \`quality\` 与 \`result\` 的区别` 这一整段（从该标题到 `# 不要做的事` 之前）替换成下面内容。

**其余段落一个字不动**（输出形状、判定标准 1–5、不要做的事）。

```markdown
# 活动类任务：结果不达标就是失败

活动类任务（考试、面试、比赛、评审这类）看的是**结果**，不是"过程有没有做完"。
任务描述里通常写清了达标条件，例如"60 分及格""进前三""拿到证书""通过面试"。

判定顺序：

1. **先从任务标题与描述里找出达标条件。** 描述写了就必须按描述判；
   没写才按常识：考试、测验看及格线（多数为 60 分）；比赛、竞赛看有没有名次或奖项；
   面试看是否通过或录用；其它活动按"有没有达成这件事的基本目的"。
2. **证据里能不能看到结果本身？** 也就是成绩单、分数截图、证书、名次榜、录取通知、
   评分截图这类东西。**只看到"我在考场""我在比赛现场"不算结果。**
   - 看不到结果 → `need_evidence`，`followup` 要具体的东西（"发一下成绩单"）。
   - 看得到结果 → 进入第 3 步。
3. **拿这个结果与达标条件比：**
   - 明显好于条件（高分通过、拿了更好的名次） → `pass` + `result: "exceeded"`
   - 刚好达到条件 → `pass` + `result: "met"`
   - **`quality` 一律填 `"met"`**，活动不看完成度。
4. **结果低于达标条件 → `fail` + `result: "below"`。**
   这时 `reason` 必须写清差在哪（"总分 48，低于 60 分及格线"），
   **不要写"不理想""有待提高"这种没有数字的空话**。

注意：活动类任务**不存在"做得认真所以算完成"这条路**。没及格就是没完成，没拿到奖就是没完成。

# 非活动类任务

非活动类任务的 `result` **一律填 `null`**，上面的规则不适用。
```

**同一文件里还要删掉旧表格的两行内容**：

- 「用户什么都没说 → `met`（不猜，也不追问）」——这条与本单冲突，改成 `need_evidence`（已在上面的新段落里表达）。
- 「用户说了结果，不理想 → `below`」——保留语义，但 verdict 必须是 `fail`（已在新段落里写死）。

## §2 第二层：`toVerdict` 归一化

`src/main/ai/pipelines/review.ts` 的 `toVerdict(raw, type)`：

- 在函数体最前面算一个 `verdict`：
  - 若 `type === 'event'` 且 `raw.result === 'below'` → `'fail'`
  - 否则用 `raw.verdict`
- 后面所有用到 `raw.verdict` 的地方（`scored` 判定、`gaps` 判定、返回值）**全部改用这个 `verdict`**。
- 注释写清原因：模型可能返回 `pass + below`（旧 prompt 留下的习惯），活动的不达标必须以 `fail` 收口，不能指望模型自己改。

**不改的部分**：`hardGateOf`、`buildReviewRequest`、`taskBrief`、`toDataUrl` 一律不动。

## §3 第三层：`completeTask` 兜底

`src/main/services/taskService.ts` 的 `completeWithPoints`：

在 `assertCompletable(task)` 之后、证据闸门之前，加一条：

```
若 task.type === 'event' 且 result === 'below'
  → throw appError('CONFLICT', '活动结果不达标不能完成，应判失败')
```

- 错误码必须是 `CONFLICT`（不是 `INVALID_INPUT`）：入参合法，是任务不该走到完成。
- `detail` 写 `type=event, result=below`。
- **不要在 `completeWithoutPoints` 里加**：那条是「不计分出口」，只是把任务标完成、不发分，不涉及结果判定。

## §4 第四层：分流不看超期

`src/renderer/main/features/tasks/reviewFlow.ts` 的 `decideReview`：

签名改成：

```ts
export function decideReview(
  verdict: ReviewVerdict,
  task: Pick<Task, 'dueAt'> & { type?: TaskType },
  now: Date
): ReviewDecision
```

判定顺序改成：

1. `verdict === 'pass'` → `'complete'`
2. `verdict === 'need_evidence'` → `'stay'`
3. **`task.type === 'event'` 且 `verdict === 'fail'` → `'missed'`**（新增，不看 `dueAt`）
4. 其余（`partial` / `fail` 的非活动任务）→ `isOverdue(...) ? 'missed' : 'revive'`（原样）

`type` 必须用**可选**字段而不是必填：现有 11 条测试直接传 `{ dueAt }`，改成必填会全红。`undefined` 时视同非活动，走第 4 条。

调用点 `runReview` 里已经是 `decideReview(verdict, loaded.data, now)`，`loaded.data` 自带 `type`，**这行不用改**。

## §9 已知影响（写给你和用户看，不要"顺手"处理）

- **`missed` 是终点**，只有归档一条出口。考试不及格后不能重考、不能撤销——要再考只能新建一个任务。用户没有要求复活路径，本单不做。
- **历史数据不受影响**：过去按 `below` 发过 0.85 折分的流水保持原样，`RUBRIC_VERSION` 只标记新口径，不重算旧账。
- **判定质量取决于模型读描述的能力**。描述里没写达标条件时，模型会按常识（60 分及格、有奖算过）判；判错时用户只能靠修改描述重新提交。
- 模型仍可能在拿不到结果时返回 `pass`。第二层归一化只能接住 `below`，接不住"根本没看到结果却判 pass"的情况——那属于 prompt 遵从度问题，不在本单范围。
