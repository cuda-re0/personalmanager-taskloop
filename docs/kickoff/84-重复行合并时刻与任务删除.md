## §1 A：把两行合成一行，去掉「每日」前缀

### 1.1 只读行

现在：

```
每日  09:35              ← .task-offsets（reminderSummary 产物）
重复  每周一、三          ← .task-repeat-row
```

改成只剩一行：

```
重复  每周一、三 09:35
```

- 整行仍是 `.task-repeat-row`，`重复` 仍是左侧 `<span>`，右侧仍是 `<button className="task-repeat-value">`（79b 的纯文字外观、手型、可点进编辑态**全部保留**）。
- 按钮文本 = `describeRepeatRule(...)` 的结果 + 空格 + `task.dailyTime`；`dailyTime` 为空/null/空串时**只显示规则文本、不加尾随空格**。
- **`.task-offsets` 这个 div 对 `type === 'daily'` 不再渲染。** 非 daily 的它照旧渲染，一个字不改。
- `reminderSummary()` 函数本身**不许改**——它还被 `TaskDraftCard.tsx` 用着（聊天里的草稿卡需要「每日 21:00」这种预览）。

### 1.2 编辑区

现有编辑控件（类型四按钮 / 每 N / 周几 / 月日 / 年月日）全部不动，**只在最后追加一个时刻输入框**：

- `<input type="time" className="task-due-edit-input task-repeat-time" />`
- **不加任何标签文字**（不加「时刻」「时间」）。它就是编辑区的最后一行。
- 值来自新加的草稿 state `repeatTime`（`string`），`openRepeat()` 里初始化为 `task.dailyTime ?? ''`。
- 与规则共用现有容器：`onBlur` / `onKeyDown` 的收起逻辑复用之（time 框在容器内，点到别处不会误提交，离开整个容器才提交）。

### 1.3 提交

`commitRepeat` 的 draft 增加一个 `timeText: string` 字段；写的 patch 变成两个键：

- `repeatRule`：原逻辑不变
- `dailyTime`：`timeText.trim() === '' ? null : timeText.trim()`

**写死**：时刻草稿非法（`''` 以外的空、浏览器没给出值）当作 `null` 提交，**不报错、不回滚**。时刻清空是合法操作（见 §2）。

### 1.4 交互不变的部分

- 点类型按钮 → 写库不关闭编辑态（79b）
- 失焦离开容器 / Enter → 写库并收起（79b）
- 草稿非法 → 不写库、收起、原值不变（79b）
- 只读行是纯文字、无边框、手型（79b）

## §2 B：空时刻 = 不提醒

`reminderPlan.ts` 现状是 `daily_time` 缺失/非法一律回落 `DEFAULT_DAILY_TIME = '09:00'`。**这条兜底作废**。

### 2.1 规则

- `dailyClock(value)` 改成返回 `{ hour: number; minute: number } | null`：正则 `^(\d{1,2}):(\d{2})$` 不匹配、或 `hour > 23`、`minute > 59` → 返回 `null`。**不再有兜底值。**
- `planRepeatReminders` 在 `rule.unit === 'D'` 的早退之后、算 `today` 之前，加一条：`clock === null` → `return []`。
- `DEFAULT_DAILY_TIME` 常量**删掉**（已确认全仓只有 `reminderPlan.ts` 自己引用，无测试引用它）。
- 用户可见效果：没填时刻的重复任务，一条提醒都不排；周/月/年规则同理。

### 2.2 `syncForTask` 的对应处理

`reminderService.syncForTask` 的 daily 分支，在 `rule.unit === 'D'` 那条早退旁边加同款早退：

```
日级（每 N 天）不提醒 → replaceForTask(taskId, [])
没有有效时刻（dailyTime 为空/非法）→ replaceForTask(taskId, [])
```

第二条**必须**用 `replaceForTask(taskId, [])`（清空），不能用 `ensureRepeatRows`——用户把时刻删掉时，旧时刻的行必须全部消失，否则照样会弹。

## §3 C：改时刻要清掉旧时刻的提醒行

### 3.1 `ensureRepeatRows` 增加时刻维度

现状签名 `ensureRepeatRows(taskId, rule, rows)`，清理条件只有 `repeat_rule <> rule`。改成：

```
export function ensureRepeatRows(
  taskId: string,
  rule: string,
  clock: string,          // 目标本地时刻 'HH:mm'，由调用方算好传入
  rows: Omit<ReminderInsert, 'taskId'>[]
): Reminder[]
```

`clock` 由 `reminderService.syncForTask` 传入，取值就是 `task.dailyTime` 归一后的 `HH:mm`（和 `planRepeatReminders` 用同一个 `dailyClock` 结果拼成字符串，**不要各自解析一遍**）。

### 3.2 清理规则（三步，顺序写死）

在一个 `tx()` 里依次：

1. **规则不符的删掉**：现有那条 `DELETE ... AND (repeat_rule IS NULL OR repeat_rule <> ?)`，参数仍是 `rule`，**逐字不动**。
2. **时刻不符的整体删掉**：读该任务 `offset_min IS NULL AND status IN ('active','paused')` 的现有行，取每行 `fire_at` 的**本地** `HH:mm`（`new Date(fireAt)` 取本地分量，**不许切 ISO 字符串**）。若「现有行非空」且「没有任何一条的本地 `HH:mm` 等于 `clock`」，说明时刻被改过 → 把这些行全部删掉（`status IN ('active','paused') AND offset_min IS NULL`）。否则（有匹配、或本来就没行）什么都不删。
3. **补插缺失**：现有 `existing` 集合 + `INSERT` 循环，**逻辑不动**。

**为什么用「一条都不匹配才全删」而不是逐条比对时刻**：用户点「稍后提醒」会把某条 `fire_at` 改到别的时刻且仍是 `active`。逐条比对会把这条 snooze 抹掉。而「一条都不匹配」只会命中"时刻整体改过"这一种情况，正常补建时必然有大量行匹配，snooze 得以保留。

### 3.3 `syncForTask` 的接线

daily 分支里 `ensureRepeatRows(taskId, rule, repeatRows)` → `ensureRepeatRows(taskId, rule, clock, repeatRows)`。

`clock` 的算法：拿 `dailyClock(task.dailyTime)` 的结果，`null` 时走 §2.2 的早退（走不到这里），非 null 时格式化成 `HH:mm`（个位数补零）。

**不许**在 `reminderRepo` 里重新解析 `dailyTime`——`reminderRepo` 不 import 业务规则，它只收一个字符串。

## §4 D：任务删除入口

### 4.1 main 侧一行不改

`taskService.removeTask`、`CH.task.remove`、`guards.g.remove`（`z.object(idInput)`）、preload `task.remove({ id })`、`task.removed` 广播、渲染层 `useTasksData` 对 `task.removed` 的重拉 —— **全部已就绪，一律不动**。

### 4.2 `useTasksData.ts` 增加一个动作

`TasksActions` 接口加：

```
/** 软删任务（→ discarded，不可恢复）。成功后收起详情 */
removeTask(taskId: string): void
```

实现要点：

- 调 `window.api.task.remove({ id: taskId })`
- 成功（`res.ok`）→ `setExpandedId(null)` 收起详情（**必须**：任务已从列表消失，详情留在屏上会指向一个不存在的 id）
- 失败 → 走现有 `setNotice` 那套行内红字（`res.error.message`），**不新增文案**
- `.catch` 里 `console.error`，同现有 `updateTask` 的写法

### 4.3 `TasksPanel.tsx` 的 UI

详情区底部、现有 `task-detail-actions` / `task-confirm-bar` 那一块，扩展成：

**显示条件**：`task.status` ∈ `['todo', 'doing', 'pending_review', 'reviewing']`（与 `stateMachine` 允许迁到 `discarded` 的来源状态一致）。`done` / `missed` / `discarded` / `archived` **不显示删除按钮**。

**未确认态**（新增 local state `deleteConfirm: boolean`，默认 false）：

```
<div className="task-detail-actions">
  {完成按钮（仅非 daily 且原条件成立时渲染，一字不动）}
  <button className="btn btn--ghost" onClick={() => setDeleteConfirm(true)}>删除</button>
</div>
```

**确认态**（`deleteConfirm === true`）：整个 actions 区换成

```
<div className="task-confirm-bar">
  <button className="btn btn--primary" onClick={confirmDelete}>删除</button>
  <button className="btn btn--ghost" onClick={() => setDeleteConfirm(false)}>取消</button>
</div>
```

- `confirmDelete`：调 `actions.removeTask(task.id)`，然后 `setDeleteConfirm(false)`
- 确认态下**不渲染**「完成」按钮（跟现有 `confirming` 分支同一个处理方式）
- 两态互斥：`confirming`（完成确认条）与 `deleteConfirm` 不会同时为 true——进入删除确认时若 `confirming` 为真，先 `actions.cancelComplete()`
- **CSS 零新增**：`.task-detail-actions` 与 `.task-confirm-bar` 已经有 `display:flex; gap:8px; justify-content:flex-end`，直接复用。`btn btn--ghost` / `btn btn--primary` 是既有类

### 4.4 文字白名单

本单**只允许新增两个界面词**：`删除`、`取消`。除此之外零新增界面中文串——不加「确认删除？」「不可恢复」「确定要删除吗」这类说明，不加图标，不加 tooltip。
