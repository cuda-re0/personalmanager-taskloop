## 交付

1. **`task.promoteDraft({messageId, localId, patch?})` 端到端**：从 `messages.meta_json` 读指定 draft → 复用 `createTask` 落库（status `todo`）→ draft 的 `steps` 写成子任务 → meta_json 标 `promoted: true` → 返回 `Task`。
2. **按 type 分支落库**：`deadline / event` 写 `due_at`（dueHint 是完整 ISO，读侧先过形状校验再 `new Date`，02 §1 有 V8 把 `'10-30 18:00'` 解析成 2001 年的前车之鉴）；`daily` 写 `daily_time / repeat_rule / active_from`，并立刻 `occurrenceService.ensureRange(今天, +3天)`。
3. **写操作广播**（02 §3.8）：promoteDraft / createManual 在 handler 层广播 `task.created`（含子任务各一条）+ `occurrence.created`（ensureRange 前后差集），对齐 W2 现有的 diff 模式；不许从渲染层发。
4. **重复确认幂等**：同一 draft 第二次确认（含绕过 UI 直接调通道）返回已生成的原 Task，不重复落库、不报错。02 §3.2 没写这条，是本轮架构方补定——交付报告里提醒我回填契约。
5. **右栏①「当前任务」**（04 §4①）：三组分列（每日 / 限时 / 活动）、排序、就地展开详情（`detail_md` / 步骤勾选 / 提醒偏移 / `[完成]`——没有类型入口，别加）、确认条而非弹窗。
6. **`task.update / transition / reorder / setReminderOffsets` 的 UI 接线**：改完调通道即可，W8 之前 reminders 不跟变是正常的。
7. **`PENDING_CONFIG` 接 `bootstrap.settings.points.*`**：完整 `PointsConfig`，不许只传 `dailyBase`，不许落回 `DEFAULT_CONFIG`（02 §5.2b：用户改过 `difficultyBase` 后卡面 +35 / 落库 +30 就是这类 bug）。

## 红线（审核逐条查，违反即打回）

1. **guard 闸门**：进 TABLE 前先写 `g.promoteDraft` zod schema；`patch` 里不许有 `type`——schema 层面就剥掉/拒绝。落库后不可改类型（02 §3.2），`TaskPatch` 没有 `type`。
2. **pointsPlanned 同源**：写库值 = meta_json 里 `draft.pointsPlanned`（生成时已按口径算好，02 §1 要求卡面值与落库值完全一致）；`patch` 带 `difficulty` 时同事务重算（`daily` 恒 `cfg.dailyBase`，传入值忽略、`< 1` 照旧拒）。非法 type×difficulty 只拒 `INVALID_INPUT`，主进程不归位（`snapDifficulty` 是渲染层的事）。
3. **完成入口唯一**：右栏 [完成] 走 `task.transition(to: 'reviewing')`；`transition({to:'done'})` 恒 409；`task.complete` 是 W6 的通道、未注册——不许调不存在的通道假装完成，更不许渲染层自己写 `completed_at`。
4. **提醒红线**：不实现、不调用 `syncForTask`（W8 的）；渲染层绝不拼提醒逻辑；改类型连带重排提醒正是"落库后不可改类型"的原因（02 §3.2）。
5. **文案纪律**：右栏、确认条、错误提示的每个串先查 `04 §1.1 / §1.2`；没有登记的报架构方补登记再用，不许自己写。
6. **测试值不是真理**：期望值与 02 公式冲突，以 02 为准并报告。
