# 开工词总目录

> 用法：**整份复制**给对应的 AI，不要节选、不要改写。开工词里的约束被删掉一半，对方就会自由发挥。
> 每份都是自包含的：项目路径、必读章节、改哪、做什么、怎么验收、不许干什么，都在里面。
>
> **篇幅分配（v0.31 起硬性执行）：规格写细，验收写短。** 见 §13。

## 2. 为什么第 1 波能开 6 个

W0 做完之后，`src/shared/` 里的类型、IPC 频道表、积分公式都已经固化成代码。6 个人都 import 同一份类型，所以：

- 写界面的 3 个（`W3` `W6B-UI` `W9-UI`）**不需要等后端**，自己写 fixture 数据就能画完
- 写后端的 3 个（`W1` `W2` `W4`）互不改同一目录

**前提是它们真的用 `@shared` 的类型。** 一旦有人图省事在自己文件里重新定义一遍 `Task`，后面接口一定对不上。所以每份开工词里都写了这条禁令。

## 4. 发出去之前，你要准备三样东西

1. **智谱 API Key**（给 `W4` 用）。没有 key，`W4` 只能写完代码不能验收，那条"真机验证多模态"过不了。
2. **一个收件邮箱**（`W8B` 用，第 3 波才需要，现在不用急）。
3. **确认这台机器能联网装 npm 包**。`W0` 要装 Electron 和 better-sqlite3，装不上后面全停。

## 5. 所有 AI 共同的铁律

这五条在每份开工词里都重复了一遍，但你要知道它们是什么：

1. **只改自己目录**，碰别人文件前先问。
2. **`src/shared/**` 只读**，不许改类型、不许加字段、不许"顺手优化"。
3. **文档矛盾时停下来报告**，不许自己选一个继续做——那会在两天后变成最难查的 bug。
4. **验收项逐条自检**，没过就说没过，不许写"基本完成"。
5. **不许顺手做没要求的功能**。想加东西，写在交付说明里让我决定。

## 6. 收工怎么验收

每个 AI 交付时应该给你一张自检表（每份开工词末尾都要求了）。你把它贴回来给我，我看两件事：

- 有没有**跳过**的验收项（跳过 = 没做）
- 有没有**改了不该改的文件**（`git status` 看，比你问它更可靠）

**每波收工先 commit 再审核。** 没有基线提交，审核方看不到"改了什么"，越界改动查不出来。

第 0 波做完后，你告诉我一声，我把第 2 波的开工词写给你。**提前写没意义**——那时候 W1 的真实接口签名才出来，现在写只能写假设。

## 7. 中途要改需求，跟谁说

**统一跟我说，不要直接告诉某个模块的 AI。** 原因是需求一改，通常不止影响一个模块：

你说"任务要有优先级颜色"，听起来是 UI 的事，实际要动 `Task` 类型的 `priority` 语义、`task.list` 的排序规则、悬浮条的状态点、日历条目的标签——4 个模块。

如果你直接跟写 UI 的那个说，它会自己加一个字段或硬编码一套颜色，其他 3 个还是旧的，然后就对不上了。

### 判断标准：看它会不会动到"接口或数据"

| 改动类型 | 例子 | 找谁 |
|---|---|---|
| 动数据模型、接口、产品规则 | 加字段、改积分公式、改提醒偏移、改状态机 | **找我**，我出变更单并改文档 |
| 只动视觉、不动数据 | 颜色深浅、间距、圆角、字号、图标 | 直接跟负责那个界面的 AI 说 |
| 只动文案 | 换个措辞、按钮文字 | 直接说，但要先让我确认（文案要全项目一致） |
| 新功能 | 加导出、加统计页、加分享 | **找我**，判断放哪一波、要不要新节点 |

### 我收到需求后会做什么

1. 判断影响面：动几张表、几个接口、几个模块。
2. 改文档（00 记需求来源，01/02/03/04 改对应章节）。
3. 出**变更单**：改什么 / 为什么 / 影响哪些 W / 已交付的要回炉哪些。
4. 再决定是插进当前波，还是排到下一波。

**已交付模块的回炉，只要改的是 `src/shared/**`，就必须停下所有人**——那是公共语言，改一处 6 个人全受影响。这种情况我会告诉你"暂停派活"。

## 8. 分开造出来的东西要拼接吗

**不需要拼接。** 不是六个独立工程各造一个模块再手工合并——它们从第一天起就在**同一个仓库、同一个目录树**里长。

W0 已经把 `src/shared/` 固化成唯一接口：6 个人 import 的是同一份 `Task`、同一份 `DomainEvent`、同一份 `computePlannedPoints`。目录互不重叠，所以各写各的不会撞。

### 但需要一次"接线"，这是预期内的活

界面模块用 fixture 数据画完，后端模块用假数据跑通 IPC——这中间有几个 `// TODO(W1)` 需要换成真实调用。**这不是意外，是设计的一部分**：让 6 个人互不等待。

接线的三处：

| 位置 | 现在 | 接完 |
|---|---|---|
| `src/main/ipc/**` 的 handler | 返回假数据 + `// TODO(W1)` | 调真实的 `taskService` 等方法 |
| `src/renderer/main/features/chat/**` 容器 | 读 fixture | 读 `window.api` + 订阅事件 |
| `features/calendar/**`、`src/renderer/hud/**` 容器 | 读 fixture | 同上 |

`src/main/index.ts` **不用改** —— W0 已经预留了 `initDb()` 和 `registerIpcHandlers()` 的调用行，这是当初专门为避免两人抢改同一文件设计的。

### 接线轮谁来干

一个人，2 小时量级，不需要并行。派给那个写 IPC 的（他最清楚每个 handler 该调谁）。集成轮开工词等第 1 波收工后我再写——需要引用实际的 service 方法名。

## 9. 代码审核用哪个 AI、怎么派

见 `07-代码审核.md`，可直接复制发。

要点只有一条：**必须给它标准，不能只说"检查代码"**。只说"检查代码"，它会给你一堆风格建议（改成箭头函数、建议引入某某库），既没用还会误导你去改好代码。

那份开工词里写了它会去哪找标准（文档具体章节 + 开工词的授权目录），以及必须自己跑 `typecheck` / `lint` / `test` / `git diff --stat`。

**每轮审核前先 commit**，否则 `git diff` 是空的，越界改动查不出来。

## 10. 契约冻结与版本纪律（波次 1 起执行）

**冻结标记**：git tag `contract-v0.7`（commit `c58e0c8`）。所有施工方以这个 tag 的 `docs/` 为准。

三条纪律，破坏任一条都会导致返工：

1. **施工中不改 `docs/`。** 要改就停下来，改完升版本号、打新 tag、通知所有在跑的施工方。
   实际踩过：架构方在 W0 施工期间改了 `02 §3.0` 的注释，W0 已按旧版抄走，于是被判"不一致"，
   白跑一轮。修法不是让施工方重抄，而是**把说明写到代码块外**。
2. **代码块内的注释一经施工方抄走即冻结。** 需要补充说明，写在代码块外的正文里。
3. **契约文档不写"XX 模块需同步"这类一次性指令。** 换轮次后读者无法判断它是否还有效，
   只会得到"文档要求改、指令说不用改"的死锁。W0 就因此停手等过一次拍板。

## 11. 波次 1 的发送方式（全外部会话）

你选择 6 个外部会话各自粘贴，这意味着**没有人替你验收**。所以发送时附上这段：

```markdown
## 工作方式（请严格遵守）

1. 先读 `docs/kickoff/08-WAVE1-DELTA.md`，再读你的模块开工词。
   两者冲突以 DELTA 为准，DELTA 没提到的以 `docs/` 为准。
2. 契约冻结在 git tag `contract-v0.7`。你读到的 `docs/` 若比你的开工词还旧，
   停下来报告，不要按旧版实现。
3. 只改你被授权的目录。需要别人目录的改动，写一句需求说明交给调度方，不要自己动手。
4. `src/shared/**` 全场只读。缺字段就提变更单（要加什么 / 为什么 / 影响谁），不许自己加。
5. 交付时必须附：验收清单逐条结果（✅/❌ + 原因）、`npm run typecheck` 与 `npm run lint` 的
   实际退出码、`git status --short` 原文。只写"已完成"不算交付。
6. 不确定的地方**停下来问**，不要自己拍板。之前有施工方在"文档说 A、指令说 B"时
   停手等拍板，那个判断是对的。
```

**你不要相信它们的自检表。** 每份交付回来，你至少跑这三条：

```bash
git status --short                      # 有没有改授权目录外的文件
git diff --stat HEAD~1                  # 改了多少，和它说的一致吗
npm run typecheck && npm run lint       # 这两条最容易被"忘了跑"
```

第 3 条如果过不了，说明它交付时没真跑，其余自检项的可信度也要打折。

## 12. 一个已知的坑：6 个会话同时改同一个仓库

外部会话和子代理一样，都操作**同一个工作区**。6 个并行时会出现：

- 两个会话同时 `git add -A`，后提交的把前一个未完成的文件卷进自己的 commit
- 同时写 `git index` 报 `index.lock` 冲突
- 一个跑 `npm run build` 覆盖 `out/`，另一个正在读

**规避办法**：给每个会话指定 commit message 前缀（`feat(W1):` / `feat(W2):`…），
并要求它**只 `git add` 自己的目录**，不要用 `git add -A`：

```bash
git add src/main/db tests/db tests/shared
git commit -m "feat(W1): 数据层与 occurrence 生成"
```

如果仍然撞上 `index.lock`，等 3 秒重试即可（不是错误，是并发写锁）。

`npm run build` 这类会写 `out/` 的命令，约定**只在交付前跑一次**，不要边写边跑。

## 13. 开工词怎么写：规格写细，验收写短（v0.31）

用户原话：「就比如我只要吃个早餐包子，你却肉馅各种精做、皮又百般精细，成品确实精致美味，但对于一个普通早餐来说，太过分了。当然，你的肉不能以次代好，皮也不能漏陷。」

翻译成规矩：

| 部分 | 尺度 | 写什么 |
|---|---|---|
| §现象/§规格 | **详写，不许省** | 参数写具体数、边界写清左右开闭、状态机写全转移、失败路径写"失败时显示什么"、文字白名单逐个列、文件清单逐文件列动作。**留白=等着它自由发挥=返工。** |
| §测试 | 只锁关键行为 | 纯逻辑的函数级测试 + 结构断言。不要求逐像素、不要求为每条款式配断言 |
| §手点验收 | **1~3 条主路径** | 只写"用户会怎么用、看到什么就算对"。不写逐条点位清单、不写坐标误差容忍、不要求截图 |
| §自检表 | 3~5 行封顶 | 四命令、白名单、工作区干净。够了 |

**配比参考**：规格 : 验收 ≈ 4 : 1。反过来就是本末倒置——花在验证上的字比花在说清需求上的字多。

**不许过的两条底线**（"肉不掺假、皮不漏馅"）：
1. 实现不许偷工：该走的真实通道不许用 mock 顶、该处理的错误不许吞掉、该删的旧代码不许留兼容分支。
2. 功能不许缺角：用户描述里每一个动作（点、拖、拉、改、关）都要能真跑通，不能"先做一半后面再说"。

**补充（2026-10-30 用户纠正）**：写详细 ≠ 写代码。

> 用户原话：「让你写详细不是让你写一堆代码，然后让另一个 AI 去复制粘贴，你最多写个伪代码，
> 详细在标准，在做哪里，做到什么程度，怎么做，不是你去帮它做了。」

- **可以写**：现象与根因定性、接口签名与语义、常量与阈值的确切数值、边界开闭、状态机转移表、
  失败路径的可见表现、文件清单逐文件写动作、文字白名单、验收主路径、关键判定的伪代码。
- **不许写**：可直接粘贴的完整函数体、完整组件代码、完整 schema / effect / 样式块。
  判断标准——若施工词里的代码块能让对方"不思考直接粘贴就跑"，就是越界；
  它只应让对方"读完知道自己要满足什么"，实现自己写。
