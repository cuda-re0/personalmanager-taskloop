# 41 · 一张任务一个卡位 + 迟到审核结果作废（v0.41）

基线：`29f8a64`（40 已合入 `9d219b2`）。四命令 **53 文件 / 670 条**绿。

## 0. 用户报的现象与原话

「任务卡这里可以看到并没有修好，其它好像没什么问题」——截图里同一个 `测试` 任务在对话流里出现了**两张卡**：上面一张旧驳回卡，下面一张待提交卡。

用户裁定：**旧审核卡隐藏后，它那行「AI 要你补什么」搬到待提交卡上**。

## 1. 定性（三层，每一层都有据）

### 1.1 显示层：`latestReviewOnly` 只去了一半的重

v0.39 只做了「审核卡 vs 审核卡」的去重（同 taskId 只留最新一条消息）。**待提交卡不是消息**——它是渲染层从 `status === 'pending_review'` 派生的 `SubmitCard`，走 `MessageList` 的 tail。所以同一个任务可以同时占两个卡位，看起来像被审了两次。

### 1.2 库里已经存在「不该存在的审核卡」（实证）

生产库（`%APPDATA%/taskloop/taskloop.db`，只读副本查得）：

```
任务 2XXW_gV1N79_（测试 · 限时 · 10 分）：status = pending_review，updated_at = 01:51:46.809
它的第 3 条审核消息 hWqSAcYMvIZG        ：created_at = 01:51:51.752（晚 5 秒）
```

`need_evidence` 在 `reviewFlow.decideReview` 里是 `'stay'`（不流转），而 `reviewing` 在 `stateMachine.EDGES` 里**没有**通往 `pending_review` 的边。也就是说：**这张卡是在任务已经不在 `reviewing` 之后写进库的**。

### 1.3 主进程：落卡前不校验状态（代码事实）

`aiService.review()` 的结构是「读任务 → 硬闸门/AI → `appendReviewMessage()`」，**落卡前不重读任务、不校验 `status`**。所以只要审核调用在任务离开 `reviewing` 之后才返回，它照样落一张卡。`reReview`（`useChatData`）也没有前置校验。

顺带一个更重的隐患，本单一起堵：`runReview` 用**调 AI 之前**的快照决定 `complete / revive / missed`，**AI 返回后不再重读**。一个迟到的 `pass` 会给已经被取消的任务发分。

## 2. 一任务一卡（纯函数 + 派生）

### 2.1 `chatViewModel.ts`：改名并加一个必填参数

`latestReviewOnly(messages)` → **`visibleChatMessages(messages: Message[], hiddenTaskIds: ReadonlySet<string>)`**

改名是为了不撒谎：它现在要管两件事，叫 `latestReviewOnly` 会让人以为只做去重。**第二个参数必填，不给默认值**——给了默认值，下一个人忘了传就会静默退回旧行为。

规则（按顺序判断一条消息）：

1. 不是 `task_review` → 保留。
2. 是 `task_review`，且 `hiddenTaskIds.has(meta.taskId)` → **丢弃**（该任务已有待提交卡占位）。
3. 是 `task_review`，但不是该 taskId 的**最后一条** → 丢弃（v0.39 原有规则）。
4. 其余保留。

头注释写清两个丢弃理由与「只过滤渲染数组，`messages` 全量不动」，并说明这张表按 `taskId` 而不是按消息 id 隐藏。

### 2.2 `chatViewModel.ts`：新增纯函数 `latestNeedEvidenceHint`

`latestNeedEvidenceHint(messages: Message[]): Record<string, string>`

- 倒序扫，每个 `taskId` **只取第一次遇到的那条**审核消息（= 该任务最新的审核）。
- 那条的 `verdict.verdict === 'need_evidence'` 且 `verdict.followup` 是非空字符串 → 记 `taskId → followup`。
- 否则（最新是 pass / partial / fail，或 followup 是 null）→ **不记这个 key**（不是记空串）。

放同文件，纯函数，入参出参不可变，测试直接调（`tsconfig.test.json` 没有 DOM）。

### 2.3 `useChatData.ts`

- 新增 `const submitTaskIds = useMemo(() => new Set(pendingSubmit.map(t => t.id)), [pendingSubmit])`；`pendingSubmit` 已经是「主进程真值 ∪ 提交中快照」，所以**提交中那几秒也不会闪回旧卡**。
- `visibleMessages` 改为 `visibleChatMessages(messages, submitTaskIds)`，依赖数组两样都写上。
- 新增 `const needEvidenceHint = useMemo(() => latestNeedEvidenceHint(messages), [messages])`。
- `ChatData`（`chatTypes.ts`）加字段 `needEvidenceHint: Record<string, string>`，注释写「taskId → 最近一次驳回要求补什么；没有这个 key 就不显示理由行」。

## 3. 待提交卡显示驳回理由

`SubmitCard.tsx`：

- 新增必填 prop `hint: string | null`，注释写清来源（`latestNeedEvidenceHint[task.id]`）。
- 渲染位置：`.review-head` **之后**、`<EvidencePanel>` **之前**。
- `hint` 为 null → 整行**不进 DOM**（不是空 `<p>`、不是 `display:none`）。
- 类名复用 **`.review-reason`**，**不新增任何 CSS**（与审核卡的 reason 行同字号同色，这是"同一句话换个位置"不是新元素）。
- 不许改 `[取消]` / `[提交]` / `还没有证据` / `EvidencePanel` 的任何一行。

`ChatPanel.tsx`：`<SubmitCard … hint={data.needEvidenceHint[task.id] ?? null} />`。

## 4. 主进程：迟到的审核结果不落卡

`src/main/services/aiService.ts` 的 `review()`：

- **两个落卡点**都要加校验：硬闸门分支（`gate !== null`）和正常 verdict 分支。**不许只改一处**——硬闸门也会落卡。
- 落卡前**重读任务**（`taskService.requireTask(task.id)`，函数开头那次快照不算，它是调 AI 之前的）。
- 重读到的 `status !== 'reviewing'` → **不落卡**，`console.warn` 一行（带 taskId 与新状态），**仍然把 verdict 正常返回**给调用方。
- **不改 `ai.review` 的返回类型**（契约不动，`ReviewVerdict` 原样）。作废与否由渲染层在 §5 里自己重读判断。

## 5. 渲染层：迟到的审核结果不执行流转

`src/renderer/main/features/tasks/reviewFlow.ts` 的 `runReview()`：

- AI 成功返回后、`decideReview(...)` **之前**，重读任务（`api().task.get`）。
- 重读失败（`!ok`）→ `return { kind: 'skipped' }`，只 `console.warn`，不弹错误。
- `status !== 'reviewing'` → `return { kind: 'skipped' }`：**不 `complete`、不 `revive`、不 `missed`、不 transition**。
- `ReviewRunResult` 已有 `'skipped'` 成员，**不加新状态**；`inFlight` 的清理顺序保持现在的 `finally`。
- `reviveToDoing` / `transitionQuietly` / `decideReview` / `countNeedEvidence` / `mergePendingSubmit` **一行不动**。

## 8. 验收（两条真机，不需要造 missed）

1. **同一任务只剩一张**：拿一条限时任务 → 完成 → 传图 → 提交 → 被驳回（或直接取消）→ 让它回到「点完成」可用的状态 → 再点完成。此时流里**只有一张待提交卡**，没有它的旧驳回卡；卡内标题下方有那行驳回理由。再点取消 → 卡消失，理由行一并不留。
2. **通过后不回魂**：提交并走到 pass → 该任务只剩一张通过卡；刷新/重开面板仍然只有一张。
