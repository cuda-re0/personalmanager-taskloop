## 0. 用户裁决（原话，不要再问）

1. 「必须过审才计分」——deadline / event 完成任务必须通过 AI 审核才能拿到积分。

3. 「回到进行中，限时和活动任务超时则判失败」——审核不通过时任务回 `doing`；若该任务 `due_at` 已过，直接判失败。

## 1. 现在的行为（改之前先认清起点）

```
点完成 → task.transition({to:'reviewing'}) → task.complete({quality:'met'}) → 直接计分
```

中间没有审核。`requires_evidence=1` 的任务会被闸门拦下、停在 `reviewing`，界面唯一出口是「直接标记完成（不计分）」——也就是这类任务现在只能拿 0 分或永远做不完。

审核卡组件 `TaskReviewCard.tsx` 已存在、由聊天流渲染，但卡片上的动作在 `useChatData.ts` 里是空函数（`TODO(W5)` 三处：证据、`ai.review`、带证据的 `complete`）。

## 2. 目标流程（deadline / event）

```
点完成
  → transition({to:'reviewing'})          // 已有，不改
  → ai.review({taskId})                    // 新增：提交即送审，不需要用户再点一次
  → 按 verdict 分流（见下表）
```

分流表（**写死，不许自己加分支**）：

| verdict | 动作 | 结果 |
|---|---|---|
| `pass` | `task.complete({ id, quality: verdict.quality ?? 'met' })` | `done` + 按该档计分 |
| `partial` | **不计分**。`due_at` 已过 → `transition({to:'missed'})`；否则 `transition({to:'doing'})` | 回进行中可补全再交；卡片逐条显示 `gaps` |
| `fail` | 同 `partial`（不计分、同样两条分支） | 回进行中；卡片显示 `reason` |
| `need_evidence` | 不流转，停在 `reviewing` | 卡片显示追问（`followup` 非空取它，否则取 `reason`），用户补证据后再点提交 |
| 请求失败（未配置 key / 网络 / 超时 / 模型报错） | 回 `doing` + 行内显示 `AppError.message` 原文 4s | **不许把任务卡在 `reviewing`**：卡住等于任务永远无法结束 |

只有 `pass` 计分。`partial` 与 `fail` 的**流转完全相同**，区别只在卡片展示：
`partial` 逐条列 `gaps`（没做到哪几项），`fail` 显示 `reason`（为什么不行）。不要在流转上给 partial 开特例。

补充约束：

- 审核进行中（从点完成到 verdict 返回）按钮**禁用**，不许重复点出两次请求。整个流程复用现有的 sending/禁用态写法，不新造 loading 组件。
- 不计分直通「直接标记完成（不计分）」**保留**——它是免分数的逃生口，但它不加分、也不调 `ai.review`。
- 每日任务（`occurrence.complete`）**不接审核**，一行都不动。每日打卡量太大、AI 调用成本与延迟都不合适。
- `verdict.reason` 一律原样显示，不在渲染层另写句子。

## 3. 证据（第一次真正接通附件存储）

> 注意：聊天输入框里现有的 `toAttachment()` 只造了本地预览对象（`local-att-N`），**从未上传主进程**。
> 那条链路不在本单范围，不要顺手改。证据走下面这条真链路。

流程（每个文件一次）：

```
用户选文件/拖入
  → File 读成 base64
  → attachment.add({ name, mime, base64 })      // 返回真 Attachment{ id, kind, url }
  → task.addEvidence({ id, evidence: { kind: 'attachment', attachmentId, addedAt } })
```

- `Evidence` 的联合类型已定义在 `domain.ts`：`{kind:'text'}` 或 `{kind:'attachment', attachmentId, addedAt}`。本单只用 `attachment` 分支。
- 上传后**立即**调 `task.addEvidence` 落库，不做「先攒着、提交时一起写」——草稿丢了证据就丢了。
- 大小与 mime 校验在主进程已有（`FILE_TOO_LARGE` / `UNSUPPORTED_MIME`），渲染层**不重复校验**，直接把 `AppError.message` 原样显示 4s。
- 已加的证据在卡片里列出：文件名 + 移除按钮（`task.addEvidence` 没有删除分支，移除只做 UI 层不落库——若做不到就**不显示移除按钮**，不许造出不生效的按钮）。
- 证据入口文字固定为 `添加文件`（新文案，登记进 04 §1.2）。卡片上已有的 `证据` 二字不动。

## 4. 新增状态 `missed`

`tasks.status` 是 TEXT、**无 CHECK 约束**，所以不需要迁移，只改类型与状态机。

| 位置 | 改法 |
|---|---|
| `TaskStatus` 类型 | 加 `'missed'` |
| 状态机 `EDGES` | `reviewing` 增加 `'missed'`；其它状态的边**一律不加**（missed 是终点，只能往 archived 走） |
| 状态机 `LABEL` | 加 `missed: '未完成'`（只用于错误消息文案，不上界面） |
| `taskStatusSchema`（guards） | 值域加 `'missed'` |
| ① 任务列表查询 | `status` 数组加 `'missed'`——**必须能看见**，否则判失败的任务凭空消失 |
| HUD 的 `ACTIVE_STATUS` | **不变**（悬浮窗只显示今天要做的事，不显示失败） |

`missed` 的显示规则（与 `done` 同档处理，不加任何文字）：

- 沉到列表底部、整行降透明度（复用 v0.27 给 `done` 的那套样式，不新写视觉）。
- 勾选框禁用；右列留空。
- 不计分、不写 ledger、不计入完成率（`transition` 本身不写流水，天然满足，不用额外做）。

判失败的判定口径：**只在审核驳回时判**。`due_at` 已过即判 `missed`；`due_at` 为 null（无截止时间）不判失败，一律回 `doing`。不做定时扫描、不做后台调度——那是 W8 的事，本单不碰。

## 6. 测试（锁关键行为，不逐像素）

纯逻辑（能测的都测）：

1. 分流函数：给定 verdict + `due_at` 已过/未过，返回正确的动作（complete / missed / doing / 停在 reviewing）。四种 verdict × 两种超时状态 = 8 条。
2. 请求失败 → 动作是「回 doing + 报错」，不是停在 reviewing。
3. 状态机：`reviewing → missed` 允许；`todo → missed`、`done → missed` 拒绝。
4. `missed` 不计分：走一遍 transition 后 `points_awarded` 为空、ledger 无新行。

结构断言（渲染层）：

- `useTasksData` 的完成路径里出现 `ai.review`，且 `task.complete` 调用点带 `quality`；
- `useChatData` 里不再有 `TODO(W5)` 三处；
- 证据上传链路里出现 `attachment.add` 与 `task.addEvidence`，顺序是 add 之后才 addEvidence。

## 7. 验收（三条主路径）

1. **需要证据的任务**：建一条 `requires_evidence=1` 的限时任务 → 点完成 → 卡片出现追问 → 点「添加文件」选一张图 → 证据出现在卡片里 → 再提交 → AI 判通过 → 任务变已完成、积分增加。
2. **普通任务**：点完成 → 不再瞬间加分，先走审核 → 判 `pass` 才加分；审核中按钮不可重复点。
3. **驳回**：让 AI 判 `partial` 或 `fail`（例如只做一半）→ 任务回到进行中、**分数不变**，可再次提交；
   把一条**已过截止时间**的任务驳回 → 该任务出现在列表底部、变淡（`missed`）、分数不变。
