## 1. 用户裁决（原话，不要再问）

1. 「必须过审才计分」——deadline / event 完成任务必须通过 AI 审核才能拿到积分。
2. 「证据」= **文件/图片附件**。
3. 「回到进行中，限时和活动任务超时则判失败」——审核不通过时任务回 `doing`；`due_at` 已过则判 `missed`。
4. 「部分完成不算通过、不发分」——`partial` 与 `fail` 流转完全相同，只是卡片展示不同。
5. **证据不可删**（v0.35 追加）：没有删除通道就不给按钮。

## 2. 数据链（本单最容易做错的一节）

现状（已核对，不要复读）：

- `useChatData.ts:193-207`：`tasks` 来自 `FIXTURE_TASKS`（`:195`），`evidence` 同样（`:200`），`needCount` 硬编码 `{ 'task-report': 3 }`（`:204`）。`tasks` 是 `useState` 只播种、没有 setter。
- `:276-277`：`const task = tasks[message.meta.taskId]; if (!task) continue` → 真任务的审核消息一律不渲染。
- `messages` 只在 `app.getBootstrap` 成功时整体替换（`:234`），没有任何事件订阅。

改法六条，**缺一条验收就过不了**：

**(a) 任务来源换成 `task.get`**
删掉 `tasks` / `evidence` / `needCount` 三个 fixture 派生量，改为：

- `taskById`：`Task` 缓存（`useState<Record<string, Task>>`，合并更新）
- `attachmentById`：`Attachment` 缓存（同上）
- `missing`：`useRef<Set<string>>`，记录取不到的 id，**不再重试**（否则每次渲染都重打 IPC）

需要哪些 id：`messages` 里 `meta.kind === 'task_review'` 的 `meta.taskId`，去重后**并发**拉取（一次 `Promise.all`，不许 for-await 串行）。拉取失败 → 该卡片不渲染 + `console.warn` 一次 + 记进 `missing`。
刷新时机四处：① 首载拿到 bootstrap 消息之后；② 收到 `task.created` / `task.updated` 且 `task.id` 已在缓存里 → 用事件载荷整体替换（**不额外打 IPC**）；③ 卡片动作（加证据 / 重新审核 / 不计分）返回后重取该 id；④ 收到新的 `task_review` 消息（见 (c)）→ 拉该 `taskId`。

**(b) 证据视图**
`ReviewView.evidence` 由 `task.evidence` 逐条转换。`kind:'attachment'` 的条目要 `Attachment{url, kind, mime}`，来源 = `attachmentById`；缺失时用 `attachment.get({ id })` 补拉（同样并发、同样进 `missing`）。
**取不到 `Attachment` 的条目直接跳过不渲染**，`console.warn`，不造占位符、不写「附件失效」这类新文案。
`toEvidenceViews` 改成纯函数：入参是 `Evidence[]` + 附件缓存，**不许在渲染函数里发 IPC**（导出以便测试）。

**(c) 审核消息实时化**
`useChatData` 挂 `window.api.onEvent`，**只处理** `type === 'message.appended' && message.meta.kind === 'task_review'`：按 `message.id` 去重后追加到 `messages` 末尾。其它事件类型一律忽略——发送链路的实时化不在本单范围，别顺手做（乐观消息与 `message.appended` 会撞出两个气泡）。卸载时 `off()`。

**(d) `needEvidenceCount` 改为派生**
删掉 fixture 与 `needCount` state。改为从 `messages` 计算：取该 `taskId` 的 `task_review` 消息，**从最后一条往前数**连续 `verdict.verdict === 'need_evidence'` 的条数，遇到第一条非 `need_evidence` 立即停。

**(e) 陈旧卡片只读**
同一任务补证据后重审会产生新的一条 `task_review`。**只有该 taskId 最后一条**（从 `messages` 末尾方向扫到的第一条）卡片带动作按钮；更早的卡片只显示 `reason` / `gaps` / 证据，动作区为空。`ReviewView` 加 `isLatest: boolean`。
理由：不然三张旧卡都能点「重新审核」，一次操作连发三份 AI 请求、落三条消息。

**(f) fixture 处置**
`FIXTURE_TASKS` 不再被引用即可（`FIXTURE_MESSAGES` / `makeBulkMessages` 压测路径保留，只是这些假消息的审核卡不再渲染）。**不许删 `__fixtures__/messages.ts` 里的数据**，只删引用。

## 3. 流程

### 3.1 提交 → 送审

```
点完成（① 行内 [完成] / 确认条上的 [完成]）
  → transition({ to:'reviewing' })        // 已有；同态是幂等 no-op
  → runReview(taskId)                     // 新增，见 3.4
  → 按 verdict 分流（3.2）
```

### 3.2 分流（写死，不许自加分支）

| verdict | 动作 | 结果 |
|---|---|---|
| `pass` | `task.complete` | `done` + 按该档计分 |
| `partial` | 不计分。`due_at` 已过 → `transition({to:'missed'})`；否则 `transition({to:'doing'})` | 卡片逐条显示 `gaps` |
| `fail` | 同 `partial`（流转完全一样） | 卡片显示 `reason` |
| `need_evidence` | 不流转，停在 `reviewing` | 卡片显示追问（`followup` 非空取它，否则 `reason`） |
| 请求失败 / 落库失败 | 回 `doing` + 显示 `AppError.message` 原文 | **不许把任务卡在 `reviewing`**。两种失败（`ai.review` 挂、`task.complete` 挂）走同一个兜底 |

「落库失败」指 `pass` 分支里 `task.complete` 抛错（`CONFLICT`、事务回滚、DB 错）。`EVIDENCE_REQUIRED` 在 `pass` 分支理论上到不了——`hardGateOf` 在无证据时直接判 `need_evidence`——但万一是它，也走同一条兜底，不单独立分支。

计分入参：deadline → `complete({ id, quality: verdict.quality ?? 'met' })`；event → `complete({ id, quality:'met', result: verdict.result ?? 'met' })`（02 §3.2：event 的 quality 恒传 `met`，分只看 `result`）。

### 3.3 保留不变的三条

- 「直接标记完成（不计分）」保留：任务已在 `reviewing`，直接 `task.complete({ id, noPoints:true })`，不加分、不调 `ai.review`。
- 每日任务（`occurrence.complete`）不接审核，一行不动。
- `verdict.reason` 一律原样显示，渲染层不另写句子。

### 3.4 `reviewFlow.ts`（新增，分流逻辑的唯一实现）

导出两个纯/半纯函数，两个 hook 都只调它，**不许在别处复制分流规则**：

```
decideReview(verdict, task, now) → 决策
  pass           → complete
  partial | fail → task.dueAt 非 null 且 Date.parse(dueAt) < now ? missed : revive
  need_evidence  → stay
  边界：dueAt 为 null 或解析成 NaN → 按 null 处理（revive）；dueAt 恰好等于 now → 不算超期（revive）

runReview(taskId, now = new Date()) → Promise<ReviewRunResult>
  ReviewRunResult = { kind:'done', verdict } | { kind:'error', message } | { kind:'skipped' }
  1. 并发闸：模块级 Set<taskId>；命中直接返回 skipped；finally 必删（含 throw 路径）
  2. task.get({ id }) 取 dueAt / type；失败 → { kind:'error', message: 原文 }
  3. ai.review({ taskId })；失败（!ok 或 throw）→
       该任务当前仍是 reviewing 时 best-effort transition 到 doing（抽成 reviveToDoing(taskId)，
       第 4 步复用；失败只记日志，不叠加报错）
       返回 { kind:'error', message: 原文 }
  4. decideReview 后执行：
       complete → 按 3.2 的入参调 task.complete
                  失败 → 先做与第 3 步完全相同的 best-effort 回 doing（共用同一个 helper，
                         不要在两处各写一遍），再返回 { kind:'error', message: 原文 }
                  —— 不许把任务留在 reviewing：pass 卡没有按钮，留下就是死锁
       revive   → transition({to:'doing'})
       missed   → transition({to:'missed'})
       stay     → 不流转
     后三种 transition 失败只记日志，不弹错
  5. 返回 { kind:'done', verdict }
```

`decideReview` 必须是纯函数（`now` 显式传入），测试直接调它。

### 3.5 卡片动作区（结论见 04 §3.3 v0.35/v0.36）

| verdict | 动作区 |
|---|---|
| `need_evidence`，`needEvidenceCount < 3` | 无证据：`[补证据]`；已有证据：`[重新审核]` + `[补证据]` |
| `need_evidence`，`needEvidenceCount >= 3` | 上面那组按钮 **+** 最右一颗弱化 `[直接标记完成（不计分）]`（`--text-faint`，不加说明文字） |
| `pass` / `partial` / `fail` | **空（无按钮）** |

- 「直接标记完成（不计分）」= `task.complete({ id, noPoints:true })`，不加分、不调 `ai.review`。这是 §3.3 保留的防死锁出口，只在连续 3 次 `need_evidence` 后出现（计数口径见 §2(d)）。第 4 次以后一直显示，不重置。
- 删掉「完成 +N」、「继续做」、活动的结果档下拉（`[结果 ▾]`）。原因：`pass` 已自动完成、`partial`/`fail` 已回 `doing`/`missed`，「继续做」在 `done` 上点一下等于把任务拉回 `doing` 却留着分；结果档依赖「点完成才计分」才有修改窗口，自动完成后 `task.update` 又没有 `result` 字段。
- `[+]`（证据行末）与 `[补证据]` 行为相同：都打开同一个隐藏 `<input type="file">`。
- 请求进行中按钮 `disabled`（卡片内本地 busy 状态，一次一个动作）。
- 卡片动作失败：动作区下方一行 `AppError.message` 原文，2600ms 后消失（与 ① 同一个停留值，不另造文案、不加图标）。

## 4. 证据

```
选文件 → FileReader.readAsDataURL → 去掉前缀取 base64
  → attachment.add({ name: file.name, mime: file.type, base64 })
  → task.addEvidence({ id, evidence:{ kind:'attachment', attachmentId, addedAt: new Date().toISOString() } })
  → 重取该任务 → 卡片刷新（证据多一条）
```

- 一次一个文件（`multiple` 不开）。`mime` 原样传 `file.type`（空串也照传），主进程的白名单/大小校验照旧，`UNSUPPORTED_MIME` / `FILE_TOO_LARGE` 原文显示，渲染层**不重复校验**。
- 上传后**立即** `task.addEvidence` 落库，不做「先攒着、提交时一起写」。
- **不显示移除控件**（v0.35 裁决）：`EvidenceChip` 的 `×`、`onRemove`、`actions.removeEvidence` 一并删。不许保留「点了没反应」或「本地删了刷新又回来」的按钮。
- 添加证据**不自动重审**：用户补完证据再点 `[重新审核]`（裁决原话「补完证据后再点提交」）。

## 8. 验收（四条主路径，真机手点）
