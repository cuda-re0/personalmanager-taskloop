## 一、要解决什么

往上滚永远加载不出更早的消息。取证四条（已核实，不必再查）：

1. `src/main/ipc/registry.ts:139` bootstrap 只返回 `messageService.recentMessages(30)`——首屏固定 30 条。
2. `src/renderer/main/features/chat/useChatData.ts:390` 拿到 bootstrap 后直接 `setHasMore(false)`，分页入口当场关掉。
3. `useChatData.ts:203` 的 `olderPool` 是**假数据池**：`bulkCount() === 0 ? makeOlderMessages(60) : []`。打包构建 `DEV === false` → `bulkCount()` 返回 0 → 池子里有 60 条假消息，只因 `hasMore` 被强制 false，它才没露过面。
4. `useChatData.ts:960` 的 `loadMore` 只切这个池子，`:966` 还挂着 `// TODO(W2): 换成 api.msg.list(...)`。

**主进程侧已完备，不需要改**：`api.msg.list({ before, limit })` → `messageService.listMessages`（`limit ?? 30`，`before` 走 `messageRepo.listBefore`）→ 按 rowid 游标、返回**升序**；`guards.ts:290` 已校验 `before` 为可选字符串、`limit` 为正整数。

**最大的坑**：不能只把 `setHasMore(false)` 改成 `true`。`olderPool` 在打包版里是 60 条假消息，一改就会把假数据塞进真实会话。本单的做法是把 `olderPool` 整条路径**删掉**，`loadMore` 一律走真 IPC。

```ts
export interface OlderPage {
  messages: Message[]
  hasMore: boolean

  existing: readonly Message[],
  page: readonly Message[],
  pageSize: number
```

`Message` 从 `@shared/types/domain` 导入（`import type`）。规则逐条写死：

1. `hasMore = page.length >= pageSize`。正好一页 → 认为还有；不足一页 → 到底。
2. 结果顺序：**去重后的 page 在前，existing 在后**，页内保持原顺序。不排序、不按 id 重排、不按时间重排。
3. 去重口径：丢掉 `existing` 里 id 已经出现在 `page` 中的那几条（游标重入或并发时会发生）。`page` 内部不重复即可，不需要二次去重。
4. `page` 为空 → `{ messages: existing 的副本, hasMore: false }`。
5. **不可变**：不改形参、不改元素对象、不用 `sort` / `splice` 处理入参，返回值一律是新数组。
