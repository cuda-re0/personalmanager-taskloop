## 背景与事实（已由架构方核实）

`hasMore` / `loadMore` 这套分页**从来没有在真数据上跑过**：

- `src/main/ipc/registry.ts:124` bootstrap 只返回 `recentMessages(30)` —— 首屏固定 30 条。
- `useChatData.ts:390` 拿到 bootstrap 后直接 `setHasMore(false)` —— 分页入口当场被关掉。
- `useChatData.ts:203` 的 `olderPool` 是**假数据池**：`bulkCount() === 0 ? makeOlderMessages(60) : []`。打包构建里 `DEV === false` → `bulkCount()` 返回 0 → **这个池子里有 60 条假消息**，只是因为 `hasMore` 被强制 false，它才没露过面。
- `useChatData.ts:916` 还挂着 `// TODO(W2): 换成 api.msg.list({ before, limit: PAGE })`。

现状后果（实测用户库）：44 条消息，最早 14 条看不到（含 4 张草稿卡、9 条文字），而且往上滚不会加载。

**主进程侧已经完备，不需要改**：`api.msg.list({ before, limit })` → `messageService.listMessages` → `messageRepo.listBefore`（按 rowid 游标、返回升序、锚点不存在抛 NOT_FOUND）。`guards.ts:290` 校验 `before` 为可选字符串、`limit` 为正整数。

**先讲清一个坑，别踩**：不能只把 `setHasMore(false)` 改成 `true`。`olderPool` 在打包版里是 60 条假消息，一改就会把假数据塞进真实会话。本单的做法是把 `olderPool` 整条路径**删掉**，`loadMore` 一律走真 IPC。

## 改动

### A. 新建 `src/shared/constants.ts`

```ts
/** bootstrap 首屏返回的消息条数上限；渲染层判「还有没有更早的」也用同一个数，避免两处各写一个 30 */
export const BOOTSTRAP_MESSAGE_LIMIT = 30
```

`src/main/ipc/registry.ts` 的 `messages: messageService.recentMessages(30)` 改为 `recentMessages(BOOTSTRAP_MESSAGE_LIMIT)`，并在该文件 import 处补上。

### B. 新建 `src/renderer/main/features/chat/pageModel.ts`（纯函数，可测）

```ts
export interface OlderPage {
  messages: Message[]
  hasMore: boolean
}

export function mergeOlderPage(
  existing: readonly Message[],
  page: readonly Message[],
  pageSize: number
): OlderPage
```

规则，逐条写死：

1. `hasMore = page.length >= pageSize`。正好一页 → 还有更早的；不足一页 → 到底了。
2. 结果顺序：**去重后的 page 在前，existing 在后**，页内保持原顺序。不排序、不按 id 重排。
3. 去重口径：丢掉 `page` 里 id 已经出现在 `existing` 中的那几条（游标重入或并发时会发生）。
4. `page` 为空 → `{ messages: existing 的副本, hasMore: false }`。
5. **不可变**：不 `sort` / 不 `splice` 入参数组、不改元素对象、返回值一律是新数组。

### C. `src/renderer/main/features/chat/useChatData.ts`

C1. import 调整：`makeOlderMessages` 从 fixtures 的 import 里删掉（`FIXTURE_MESSAGES` / `makeBulkMessages` 保留）；新增 `mergeOlderPage` 与 `BOOTSTRAP_MESSAGE_LIMIT`。

C2. 删掉 `:203` 的 `olderPool` ref 声明。

C3. 新增 `const [loadingMore, setLoadingMore] = useState(false)`。

C4. `:390` 的 `setHasMore(false)` 改为 `setHasMore(res.data.messages.length >= BOOTSTRAP_MESSAGE_LIMIT)`。注释写明：条数顶到上限就认为可能还有更早的，允许一次多余的空请求，比漏历史划算。

C5. `loadMore` 整体重写，只保留真数据一条路径：

- 早退：`loadingMore` 为真 → 直接 return（并发保护）。
- 取游标：`const oldest = messages[0]`；取不到（列表空）→ `setHasMore(false)` 后 return。
- `setLoadingMore(true)`。
- 调 `window.api.msg.list({ before: oldest.id, limit: PAGE })`。
- `res.ok === false` → `console.error('[chat] 翻页失败', res.error)` 并 `setHasMore(false)`。**不许**弹错误气泡、不许加可见文案。
- 成功 → `const next = mergeOlderPage(messages, res.data, PAGE)`，再 `setMessages(next.messages)`、`setHasMore(next.hasMore)`。
- Promise 链尾 `.catch`：异常时同样 `setHasMore(false)` + `console.error`；`.finally` 里 `setLoadingMore(false)`。
- 依赖数组：`[messages, loadingMore]`（`messages` 必须在依赖里，游标取的就是它；`loadingMore` 挡住同一时刻的两页并发）。

C6. 返回对象里 `loadingMore: false`（`:1003`）改为 `loadingMore`。

C7. `PAGE = 20` 保留不动。

C8. 删掉 `TODO(W2)` 那行注释（它描述的事已经做完）。

### D. `src/renderer/main/features/chat/ChatPanel.tsx`

D1. 删掉模块级 `noLoadMore` 常量。
D2. 三个分页 prop 两层统一，不再按层分叉：`hasMore={data.hasMore}`、`loadingMore={data.loadingMore}`、`onLoadMore={data.loadMore}`。
D3. 注释改写为：分页是**消息级**的，两层共用同一个池；任务层一次翻页可能全是文字、一条卡都不出现，用户需要再滚一次才会再拉一页。
D4. 其余一律不动：`key={layer}`、`tail` 只给任务层、空态判定 `chatMessages.length === 0`、`ChatInput` 在分层之外。
