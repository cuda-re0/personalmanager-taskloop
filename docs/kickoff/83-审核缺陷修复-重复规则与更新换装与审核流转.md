## 二、规格

### A · 重复规则容错与锚点判定

**A1 写入侧唯一校验点。** 所有会写 `tasks.repeat_rule` 的入口（`task.createManual` / `task.promoteDraft` / `task.update`，以及 `taskService` 内其它实际落库点）在落库前各调用一次 `parseRepeatRule`。业务校验**只放在 service 层一次**：`guards.ts:51` 的 zod 保持只管类型，不许在两处各写一份规则解析，也不许改 `guards.ts` 的 schema 形状。只写 `daily` 任务时校验；非 daily 写 `null` 的路径不校验。

**错误怎么转**（这一步单写清，不许自由发挥）：`parseRepeatRule` 抛的是裸 `Error`，message 是「重复规则格式不正确」。service 层用 `try/catch` 捕获，**吞掉原 Error，改抛 `appError('INVALID_INPUT', '重复规则格式不正确', { detail: <规则原文> })`**。不要复用原 Error、不要 push 到 `cause`、不要把原堆栈透给渲染层。`detail` 里放规则原文（便于定位），但**不许**写进任何用户可见文案。

**A2 读取侧单条隔离。** `ensureRange` 的逐任务循环里，每个任务单独做异常隔离：解析或判定失败时跳过该任务、写一条主进程日志（含 task id 与错误摘要，**不含规则原文**）、事务继续，其余任务照常补齐 occurrence。`parseRepeatRule` 的异常不得冒泡到 `tx()` 外层，不得让事务整体回滚，不得让 `getBootstrap` / `occurrence.today` / `occurrence.listByRange` 失败。`shared/repeatRule.ts` 保持零运行时依赖（不引 electron / db / react），不得为改错误类型破坏这一约束；错误码透出由 main 侧识别处理。

**A3 渲染侧兜底。** `TasksPanel` 渲染重复规则只读行时，`describeRepeatRule` 的调用必须容错：失败时该行按不可编辑的只读态处理（不渲染规则描述即可），异常不得冒泡到 React 树（全仓无 ErrorBoundary，本单不要求新建 ErrorBoundary 组件）。**不得新增任何界面中文串**，也不得因为坏值把整块任务详情藏掉。

**A4 锚点下界统一（一句话规则）。** `matchesRepeatDay` 在 `parseRepeatRule` 之后、四个 unit 分支之前统一短路：`day` 与 `anchor` 都是 `YYYY-MM-DD`，字典序即日期序，`day < anchor` 直接返回 false。W/M/Y 分支的 `weeks/months/years >= 0` 只保留周期偏移判定，不再兼职下界保护；D 分支的 `diff >= 0` 相应收敛，不要留两份判定。短月补齐、平年 `02-29 → 02-28`、W 的周一差算法、旧值 `DAILY`/`WEEKLY:` 兼容语义**一字不动**。

**A5 测试。** `tests/main/repeatRule.test.ts` 补三条：W（锚点取周三、判同周一）、M（锚点取 15 号、显式 `monthDays` 含 1、判 1 号）、Y（锚点取年中、指定 `01-01`、判当年 1 月 1 号）各断言「锚点前 false、锚点当日与下一周期首日 true」。另在 occurrence 层测试补一条：库里存在一条非法规则的 daily 任务时，另一条合法任务仍能通过 `listToday` / `listRange` 正常补齐，且非法任务不产生 occurrence、不抛异常。

### B · 更新换装安全

**B1 载荷内容校验（阈值写死）。** `parsePayload` 对每个 value 做 base64 合法性校验：字符表只允许 `[A-Za-z0-9+/=]`、`=` 只能出现在尾部且最多两个、串长对 4 取模必须为 0、解码后长度非零。任一不符抛错并走既有失败路径（清 staging + `resetAttempted`），**禁止 `Buffer.from` 静默截断**。上限：单文件解码后 **8 MiB**、整包解码后 **32 MiB**、文件数 **200**；超出同样抛错。目录穿越的现有双重防护（`assertSafeKey` + `startsWith(prefix)`）一字不动。

**B2 下载上限。** `downloadPayload` 不许无界 `res.text()`：按 Content-Length 预检、读取过程中累计字节超过 **40 MiB** 立即 abort 并抛错；超时仍是既有 60 秒。失败走 B1 同一条清理路径。

**B3 覆盖后关键资源校验。** 判 `ok` 之前，在 `copyTree` 之后校验关键资源存在且非空：至少覆盖 main 入口 js、preload 入口 js、每个 renderer 的 `index.html`，具体路径按 `scripts/make-payload.mjs` 实际打包清单推导（不许写死猜测文件名）。`versionOf(pkg) === version` 仍是必要条件之一，**两者都过才算成功**；任一缺失或为空即 `ok = false` 并进入回滚，日志要写明缺哪个文件。

**B4 发布侧防线。** `make-payload.mjs` 生成 `payload.json` 前自检 B3 那批关键文件存在且非空，缺失直接非零退出、不产出 payload。不得为了让脚本跑通而放宽 B3 清单。

**B5 回滚顺序。** 备份（`out.bak` / `package.json.bak`）在确认恢复成功之前不得销毁；回滚必须「先恢复并验证到位，再清理新目录残留」，不得出现「先删新 `out`、恢复失败、两边都没了」。

写成三步固定顺序，不许调换：
1. 先确认 `out.bak` 存在且可读（否则直接判"回滚失败"，**不动任何目录**）
2. 把新 `out` 改名成 `out.failed`（**不要 `rmSync`**，失败时留着它下次启动才能查），再把 `out.bak` 改名成 `out`
3. 校验恢复后的关键资源可读（同一批 B3 清单），通过才算回滚成功；不通过则把 `out` 改回 `out.failed`、`out.failed` 改回 `out`，判"回滚失败"

`package.json` 的回滚同理：先确认 `package.json.bak` 可读，再覆盖。

**B6 回滚失败不得重启 —— 顺序写死，不许自行发挥。** 三段：

- **覆盖成功**（B3 的关键资源 + `versionOf(pkg) === version` 都过）→ `app.relaunch()` → 逐个 `win.destroy()` → `app.quit()`
- **覆盖失败、回滚成功** → `app.relaunch()` → 逐个 `win.destroy()` → `app.quit()`（用户拿到的是旧版，重启无害）
- **覆盖失败、回滚也失败** → **不调 `app.relaunch()`、不 `destroy()`、不 `app.quit()`**，只 `console.error`，保留 `out.failed` / `out.bak` / `package.json.bak` 供下次启动人工恢复

三条共同约束：`app.relaunch()` 必须在任何 `win.destroy()` **之前**调用（`window-all-closed` 会触发 `app.quit()`，之后就没机会了）；`relaunch` 全程最多调一次；第三条分支下程序**保持当前窗口继续跑**——`out` 目录此刻可能已损坏，但那是用户点「退出」之后才暴露的事，比"重启到白屏"好。

**B7 定时器纳管。** 所有 `setTimeout` 句柄必须保存并可由 `before-quit` 统一清理，覆盖 `registry.ts:165`（800ms exit 兜底）、`registry.ts:173`（2s applyUpdate）、`index.ts:64`（8s 启动自检）、`index.ts:70`（3s LHM）。`applyUpdate` 入口判断应用是否已进入退出流程，是则直接返回并清 `pending`，不得再触发换装。

**B8 尝试标记自愈。** 现有 `UpdateState.attemptedVersion` 是 `string | null`（`readState` 只认 `typeof === 'string'`）。改成带时间戳的结构，**必须同时兼容旧文件**：

- 新格式落盘为 `{ "version": "0.79.0", "at": "2026-11-06T02:40:00.000Z" }`
- `readState` 两种都认：读到纯字符串（旧文件）→ 当作 `{ version: 该字符串, at: null }`；读到对象 → 取 `version` 与 `at`（字段类型不对一律当 `null`）
- `at === null` 视为**已过期**，允许重试
- 拦截条件改为：`attemptedVersion === latest` **且** `at` 非空 **且** `now - Date.parse(at) < 24 小时` 才拦；超过 24 小时放行
- `manual: true` 始终绕过拦截（现状不变）
- 写入一律新格式，**不许**保留两套写入口
- 既有「覆盖失败后故意不清标记以防重启循环」的设计保留，过期放行时打一条 `console.warn` 说明"标记已超 24 小时，允许重试"

**B9 tag 形状。** 在 `fetchLatestRelease` 里，tag 去掉前导 `v`/`V` 之后必须匹配 `^\d+\.\d+\.\d+$`；不匹配用 `withFailure(new Error('Release 的 tag_name 形状不对'), 'shape')` 抛出（复用 78b 已有的标记，**不要新增 `failure` 取值**），于是自动路径静默视为无更新、manual 路径走既有「无法访问 GitHub」文案——**不新增任何界面文案**。不得把 `0.80.0-beta.1` 当正式版安装，不得把非数字段静默按 0 参与比较。既有 `replace(/^[vV]/, '')` 与「空串算 shape」两行保留。

**B10 错误透出。** 78b 已在 `checkUpdate` 的 catch 里按 `failure` 分了三档文案，**这三句不许改、不许减**。本单只加一件事：给 `appError` 补第三个参数 `{ detail: e instanceof Error ? e.message : String(e) }`，让 GitHub 的真实报错进 detail 而不是丢掉。不得放宽 `envelope.ts` 的 `UNKNOWN` 收口契约（`tests/ipc/envelope.test.ts` 钉着），不得改渲染层。
