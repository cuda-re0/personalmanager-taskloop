## 0. 要解决的现象（不是需求描述，是实测记录）

用户在某条任务上点 `[完成]`，**界面没有任何反应**：任务没完成、没提示、没报错。

实测链路：

1. 该任务 `requires_evidence = 1`（库里 `写季度复盘初稿` 就是）
2. `useTasksData.submitAndComplete` 先 `task.transition('reviewing')` 成功，再 `task.complete({ quality: 'met' })`
3. `taskService.completeWithPoints` 抛 `EVIDENCE_REQUIRED`（`taskService.ts:558`）
4. 渲染层 `if (!done.ok) console.error(...)` —— **只有控制台，界面上零反馈**
5. 于是用户看到的是「按钮坏了」

本轮**只修第 4 步**。证据从哪来（`attachment.add`，归 W11）与审核 UI（归 W7）不是本线的事，**不许顺手做**。

## 2. 行为规格

### 2.1 什么时候显示

`task.complete` **或** `task.transition` 返回 `ok: false` 时：

- 在**该任务行内**（不是页面顶部、不是 toast、不是 modal）显示一行红字，内容 = `res.error.message` **原样**，不加前缀、不加括号补充。
- `EVIDENCE_REQUIRED` 的文案就是 04 §1.1 已登记的 `证据不能为空`——**不许改写**（要改措辞是契约变更，归架构方）。
- 停留 `2600ms` 后自动消失。同一任务连续失败只重置计时，不叠加多行。
- 换任务操作（点别的行完成、展开/收起）不清除它，等它自己到时。

### 2.2 什么时候不显示

- `noPoints` 那条路径（`[直接标记完成（不计分）]`）成功时：不显示。
- 步骤未勾导致弹确认条时：这是正常流程，**不显示红字**。
- 失败后任务停在 `reviewing`，它仍在「限时/活动」组里（`ACTIVE_STATUS` 含 `reviewing`），红字就该落在这一行上。

### 2.3 样式

- `font-size: 12px`、`color: var(--danger)`、`padding: 2px 0 6px`、`line-height: 1.4`。
- 和积分那边的 `.points-notice` **视觉一致**，但**各自实现**（不共享组件、不抽公共 CSS 变量，两处生命周期不同：那边是全局一条，这边按 taskId 挂）。

## 3. 实现要点（容易踩的）

1. **状态形状**：`notice: { taskId: string; message: string } | null`。按 `taskId` 匹配渲染，别做成全局一条——否则 A 任务失败，B 行也红。
2. **计时器必须清**：`useRef` 存 timer，卸载时 `clearTimeout`，新失败先清旧的。`StrictMode` 下 effect 会跑两次，写成"先清后设"就安全。
3. **不要在 `setNotice` 里做副作用**，定时器放 `useEffect` 里跟着 `notice` 变。
4. `actions` 的 `useMemo` 依赖数组要同步加新回调，漏了会拿到旧闭包（v0.20 的 P1 就是这么来的）。
5. `TasksPanel` 里 `TaskDetail` 与列表行**共用**同一份 `actions`（`tasksPanelWiring.test.ts` 有一条断言：`= useTasksData()` 全文只许出现一次），**别为了便利再调一次**。


## 7. 手点验收（写进报告）

1. 找一条 `requires_evidence=1` 的任务（库里 `写季度复盘初稿`），点 `[完成]`
2. 期望：行内出现一行红字 `证据不能为空`，约 2.6 秒后消失；任务停在「待确认」，仍在列表里
3. 再点一次，红字重新出现（不是叠两行）
4. 点另一条 `requires_evidence=0` 的任务完成 → 不出现红字，正常计分
5. 有一条带未勾步骤的任务：点完成 → 弹的是确认条（不是红字）
6. 在确认条上点 `[直接标记完成（不计分）]` → 无红字，任务变 done
