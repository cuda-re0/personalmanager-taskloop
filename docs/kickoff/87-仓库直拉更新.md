## 背景（只解释目的，不要求你扩写）

现在更新靠「GitHub Release 上传 `payload.json`」：查询 `api.github.com/releases/latest` → 下载 asset → base64 解包 → 覆盖 `resources/app`。痛点是每次发版都要先 `build`、再打 payload、再上传。

改成：版本与文件清单直接从仓库读（`raw.githubusercontent.com`），`git push` 即发布。Release 那条路**保留作为回退**（旧版本升级、raw 不可达时用）。

## 二、新增 `src/main/update/repoSource.ts`

从仓库 raw 读清单、下载文件。**全部走 `net.fetch`（Chromium 网络栈）**，不要用裸 `fetch`。

### 2.1 常量与接口

- 复用 `github.ts` 里已有的仓库标识：把那里的 `OWNER` / `REPO` 改成 `export const`（只加 `export`，值不动），本文件 import 使用，**不要复制一份字符串**
- raw 基址：`https://raw.githubusercontent.com/${OWNER}/${REPO}/master`
- 导出：
  - `interface RepoManifest { version: string; files: string[] }`
  - `parseRepoManifest(raw: string): RepoManifest`（纯函数）
  - `fetchRepoManifest(fetchImpl?): Promise<RepoManifest>`
  - `downloadRepoTree(manifest, stagingDir, fetchImpl?): Promise<number>`

### 2.2 `parseRepoManifest` 的校验（每条不过就抛错，错误信息要指名哪一条）

1. 合法 JSON 且是普通对象（非数组、非 null）
2. `version` 是字符串且匹配 `^\d+\.\d+\.\d+$`（与 `github.ts` 里 tag 形状同口径）
3. `files` 是非空字符串数组，长度 ≤ 200
4. 每个元素过安全校验：非空、不含反斜杠、不是绝对路径（不以 `/` 开头、不匹配 `^[A-Za-z]:`）、按 `/` 切分后不含 `..`
5. 元素不得重复（重复即抛错，不做静默去重）
6. 必须**恰好包含**第 1.3 条那 5 个关键文件（少一个就抛错：清单不全装完必白屏）

### 2.3 `fetchRepoManifest`

- `GET ${RAW}/out/manifest.json`，10 秒超时（`AbortController`）
- 状态码分档，错误对象上挂 `failure` 字段（与 `github.ts` 的 `FailureKind` 同名字段，便于上层分档）：
  - 404 → `'notfound'`
  - 其它非 2xx → `'http'`
  - 请求抛错/超时 → `'network'`
  - 解析或校验不过 → `'shape'`
- 响应体上限 1 MiB（超过按 `'shape'` 处理）

### 2.4 `downloadRepoTree(manifest, stagingDir)`

- 严格按 `manifest.files` 的顺序**串行**下载（不做并发，14 个文件不需要）
- 目标路径：`<stagingDir>/out/<rel>`，先 `mkdirSync(dirname, {recursive:true})`
- 每个文件：`GET ${RAW}/out/${rel}`，10 秒超时；非 2xx、0 字节、单文件 > 8 MiB 一律抛错（错误信息带 `rel`）
- 总量 > 32 MiB 抛错
- 写文件前用 `resolve` 再校验一次目标路径是否仍在 `<stagingDir>/out/` 前缀内，越界则跳过并 `console.warn`（与 `payload.ts` 的 `writePayloadTree` 同做法）
- 下载完再取 `${RAW}/package.json`，写入 `<stagingDir>/package.json`
- **最后校验**：`<stagingDir>/package.json` 的 `version` 必须**严格等于** `manifest.version`，不等就抛错（raw 的 CDN 缓存约 5 分钟，会出现「清单是新的、文件是旧的」这种半新半旧，必须挡住）
- 返回值：`out/` 下成功写入的文件数（不含 `package.json`）
- 任一文件失败：直接把错误抛给调用方，**不要**自己清 staging（调用方统一清）

## 三、`updateService.ts` 接入

### 3.1 `pending` 改成带来源

```
type PendingUpdate =
  | { source: 'repo'; version: string; manifest: RepoManifest }
  | { source: 'release'; version: string; url: string }
```

### 3.2 `checkUpdate` 的源选择顺序

1. 先试 `fetchRepoManifest()`。成功 → `latest = manifest.version`，记 `source: 'repo'`
2. 失败（任何 `failure`）→ `console.warn('[update] 仓库源不可用，回退 Release', e)`，再走现有 `fetchLatestRelease()`
3. **两个源都失败** → 沿用现有分档逻辑，一个字不改：`manual === true` 抛带 `failure` 的 `appError`（`notfound` / `network` / 其它），自动路径 `console.error` 后返回 `{ hasUpdate: false }`
4. 源成功之后的逻辑（`compareVersion`、`hasUpdate`、尝试标记、`writeState`、`pending` 赋值、四种返回）**结构与顺序一律不动**，只是 `pending` 换成 3.1 的联合类型

**不要**做「先比 repo 版本、再比 release 版本取大者」这种合并；先成功的源就是本次唯一源。

### 3.3 `applyUpdate` 只改「载荷怎么进 staging」这一段

- `source === 'repo'`：`await downloadRepoTree(pending.manifest, staging)`，返回值 0 视为失败（抛 `Error('仓库源没有可写入的文件')`）
- `source === 'release'`：保持现有 `parsePayload(await downloadPayload(url))` + `writePayloadTree`，含现有的「载荷版本与 Release 版本不一致」判断
- 两条路径产出的 staging 结构必须**完全一致**：`staging/out/**` + `staging/package.json`
- 之后的一切（`clearStaging`、`resetAttempted`、`resourcesApp` 计算、`destroy` 窗口、`out.bak` 改名、`copyTree`、版本与关键资源校验、`rollbackInstall`、`relaunch` / `quit`）**一行都不许动**

### 3.4 注释

在 `applyUpdate` 的 repo 分支上写清：CDN 缓存约 5 分钟，所以「清单新、文件旧」由 `package.json` 版本校验挡住，失败就是「这次不更新」，下次启动重试。
