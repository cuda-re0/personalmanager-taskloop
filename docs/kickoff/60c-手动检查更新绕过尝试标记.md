## §0 现象（真机验证 60b 时暴露，架构方定性）

60b 的失败路径验证完之后，`%APPDATA%\taskloop\update-state.json` 里是 `{"attemptedVersion":"0.60.0"}`，而当前版本仍是旧的。此时用户点设置页的「检查更新」：

1. `checkUpdate()` 命中「这个版本已经尝试过」分支 → 返回 `{ hasUpdate: true, applying: false }`；
2. `useSettingsData.ts:177` 的映射是 `res.data.hasUpdate ? '正在更新' : '已是最新'`；
3. 界面显示「正在更新」，但既不安装也不重启，2.6 秒后提示消失。

**这个标记的正确职责是「防自动重启死循环」，不是「禁止人工再试一次」。** 自动路径必须被它拦住；人工路径必须能绕过，否则更新失败后没有任何界面手段可自救。

## §1 改法（唯一允许的改法）

### §1.1 `src/main/update/updateService.ts`

`checkUpdate` 接收一个可选的选项对象：

```ts
export interface CheckOptions {
  /** 人工触发（设置页按钮）：跳过 `attemptedVersion` 拦截，仍然写标记 */
  manual?: boolean
}

export async function checkUpdate(options: CheckOptions = {}): Promise<CheckResult>
```

判定顺序改成（**只动「已尝试过」那一条**）：

1. 读 manifest；`null` → 返回 `{ current, latest: null, hasUpdate: false, applying: false }`。
2. `hasUpdate = compareVersion(latest, current) > 0`；不为真 → 返回，什么标记都不碰。
3. `options.manual === true` 时**跳过**下一步的拦截（但下面写标记那步照做）。
4. 否则若 `readState().attemptedVersion === latest` → `console.error` 后返回 `{ hasUpdate: true, applying: false }`（原样保留，这是自动路径的唯一防线）。
5. `writeState({ attemptedVersion: latest })` —— **人工路径同样要写**，写失败同样返回 `applying: false`（`console.error` 原文保留）。
6. 返回 `{ current, latest, hasUpdate: true, applying: true }`。

**硬规定：**

- `CheckResult` 类型一个字不改（`applying: false` 在人工路径下不再出现于「已尝试过」场景）。
- 不改 `readState` / `writeState` / `compareVersion` / `readManifest` / `runStartupUpdateCheck`。
- `runStartupUpdateCheck` 里那句 `checkUpdate()` **不带参数**，自动路径行为必须与 60b 完全一致。
- 注释要写清：`manual` 只跳过拦截，不跳过写标记——人工点一次失败后，自动路径同样不会再自动重试。

### §1.2 `src/main/ipc/registry.ts`

`app.checkUpdate` 那行 handler 里把 `checkUpdate()` 改成 `checkUpdate({ manual: true })`。

其余不动：`applying` 为真时那句 `setTimeout(() => applyUpdate(), 2000)` 保留，2 秒延迟的理由不变。

1. `npm run typecheck` 0 / `npm run lint` 0 / `npm run build` ✓。
2. `npm test` → 70 文件 / 807 条，仅 `chatBrief` 一红。
3. **真机一条（验证本单目的）**：
