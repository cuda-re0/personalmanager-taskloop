## 0. 用户手点报的三件事（原话）

1. 「任务审核有问题」——附了两张卡片的截图，卡上只有标题、一句 AI 判定语、一个「证据 +」，没有任何按钮。
2. 「在右上方的任务区不能直接提交证据？这个是怎么设计的，这里有点问题。」
3. 「为什么限时任务不需要审核，限时任务也需要。」

架构方核了库里的真值：那两条任务都是 `pass`、10 / 20 分已入账。所以**不是漏判，是它们从创建那一刻就被标成"不需要证据"，AI 没有证据可看，只能凭一句"我做完了"放行**。根因与改法见 §2。

## 1. 用户裁决（原话，不要再问）

1. 「一律要证据」——**限时 / 活动任务全部要求证据**，没有"这个任务不需要证据"的例外。每日任务不接审核，不受影响。
2. 「点击完成，然后在左侧区域生成标准的任务卡片，我提供证据后，点击提交，算整个流程」——**点完成不立即送审**。
3. 「给取消，同时超过 10 分钟就退回」。

## 2. 根因（已核实，不要复读代码找原因）

`requiresEvidence` 这个字段**唯一的写入点是 AI 草稿卡**（`parse.ts:145` 取模型的判断）。手动建任务走
`taskService.createManual`，`requiresEvidence` 恒为 `false`（`:153`）。而审核闸门 `hardGateOf`（`review.ts:35`）写的是：

```
!task.requiresEvidence || evidenceCount > 0  →  放行给模型
```

于是所有手动建的限时任务都跳到模型；prompt 的规则 4 又写着「任务不要求证据 → 按用户陈述判定，`pass` + `met` 即可」。
两道叠加的结果：**在右栏点完成、什么都不交，也能拿满分。**

同时还有两个配套问题：

- 点完成就走了 `transition('reviewing') → ai.review`，没有"用户交材料"的窗口期；用户真正想交证据时，任务已经在审核里了。
- 审核卡上的 `[+]` 无条件渲染，`done` / `missed` 的卡上仍有一颗能点的加号，而 `taskService.addEvidence`
  没有状态校验——证据能挂到已完成的任务上，卡片却没有任何重审出口。

## 3. 新增状态 `pending_review`（待提交）

`tasks.status` 是 TEXT、无 CHECK，**不需要迁移**，只改类型与状态机。

| 位置 | 改法 |
|---|---|
| `domain.ts` 的 `TaskStatus` | 加 `'pending_review'` |
| `stateMachine.ts` 的 `EDGES` | `todo` / `doing` 两个数组各加 `'pending_review'`；**新增键** `pending_review: ['reviewing', 'doing', 'discarded', 'archived']`（该映射是 `Record<TaskStatus, TaskStatus[]>`，不写这个键编译不过） |
| `stateMachine.ts` 的 `LABEL` | **新增** `pending_review: '待提交'`（穷举，只用于错误消息，不上界面） |
| `stateMachine.ts` 的 `isTransitionAllowed` | `daily` 的禁止集合从 `reviewing \| done` 扩到 `pending_review \| reviewing \| done`（错误文案沿用「每日任务不进入审核/完成状态，请完成当天的打卡」，不新增句子） |
| `guards.ts` 的 `taskStatusSchema` | 值域加 `'pending_review'` |
| 文件头状态图 | 补两行：`todo/doing ──提交完成──→ pending_review`、`pending_review ──提交审核──→ reviewing`；`pending_review ──取消/超时──→ doing` |

**为什么非要加这个状态**：如果"等用户交材料"和"AI 正在看材料"都叫 `reviewing`，§6 的 10 分钟超时会把正在等 AI 回复的任务一起打回去；
而加了之后，超时扫描只看 `pending_review`，`reviewing` 一个都不动。另一个收益是右栏能正确显示"这条我在等自己交材料"。

## 5. 流程改造（点完成不再送审）

```
右栏点 [完成]（含确认条上的 [完成]）
  → transition({ to:'pending_review' })      // 唯一动作，到此为止
  → 会话区末尾出现待提交卡（§7）
  → 用户传证据 → 点 [提交]
      → transition({ to:'reviewing' })
      → runReview(taskId)                    // 复用 kickoff/33 §3.4 的现有实现，一行不改
      → 按 verdict 分流（pass 计分 / partial|fail 回 doing 或 missed / need_evidence 停在 reviewing）
  → 或点 [取消] / 停留超 10 分钟
      → transition({ to:'doing' })           // 不发分、不调 AI
```

- `useTasksData` 里**删掉**点完成后的 `runReview` 调用，只留 `transition({to:'pending_review'})`。
  `noPoints`（直接标记完成不计分）分支保持原样，仍然一步到 `done`。
- 每日任务（`occurrence.complete`）**一行不动**。
- 提交动作放 `reviewFlow.ts` 里新增一个导出（如 `submitForReview(taskId)`），**不要在组件里直接拼两步**：
  内部先 `transition({to:'reviewing'})`，成功再 `runReview`；transition 失败返回错误原文并**不**调 AI。
  证据为零时直接返回 `null`（不提交、不报错），按钮侧本就 `disabled`，这里是兜底。

## 6. 10 分钟超时（主进程，不看前端计时器）

新增 `src/main/services/reviewSweeper.ts`：

```
startReviewSweeper(): () => void
  - 立即跑一次，然后 setInterval(60_000)
  - 每轮：listTasks({ status:['pending_review'] })
          → 过滤 updated_at <= now - 600_000（10 分钟）
          → 逐条 transitionTask(id, 'doing')
          → 每条成功后 broadcast({ type:'task.updated', task })
  - 单条失败只 console.warn，不中断本轮、不弹任何界面
  - 返回 stop()：clearInterval
```

- 在 `src/main/index.ts` 的 `app.whenReady()` 里、`registerIpcHandlers()` 之后启动；`before-quit` 时调用 stop。
  **`before-quit` 监听器要和现有的一起写，不要覆盖已有的**。
- 判据只用 `updated_at`：`transition` 写状态时会更新它（`updateColumns(id, cols, now)`），所以进 `pending_review` 的那一刻就是计时起点。
- **不扫 `reviewing`**，也不做"只在主窗可见时才扫"这类条件——窗口关着也要照常退回。
- 时钟常量写成文件顶部具名常量（`REVIEW_TIMEOUT_MS = 600_000`、`SWEEP_INTERVAL_MS = 60_000`），测试要能注入 now。

## 7. 待提交卡（渲染层派生，不是消息）

规格见 `04 §3.2b`，实现要点：

- **不落 `messages`**。它由 `status === 'pending_review'` 派生，取消/提交/超时后自然消失，历史里不留痕。
  `messages.kind` 不要加新值、不要写新消息。
- `useChatData` 新增 `pendingSubmit: Task[]`：
  - 首载 `task.list({ status: ['pending_review'] })`（与现有 bootstrap 那次可并发）；
  - 订阅 `task.created` / `task.updated` / `task.removed` 维护这份列表（`useChatData` 已经在订阅事件，往同一个 handler 里加分支）；
  - 另加 `submittingIds: Set<string>`：提交中的任务**仍留在列表里**（否则 transition 到 `reviewing` 的瞬间卡片就消失，
    用户在等 AI 的几秒里看不到任何东西）。`runReview` 返回后（无论成败）从集合里删掉。
- 排序：`updated_at` 升序（先进先出）。
- 渲染位置：`ChatPanel` 里 **`MessageList` 与 `ChatInput` 之间**，容器 `max-height: 42%` + `overflow-y: auto`。
  **不要**动 `MessageList` 的虚拟滚动（它是绝对定位的固定高度容器，塞非消息内容会把测量搞坏）。
- 新组件 `src/renderer/main/components/SubmitCard.tsx`，结构照 `04 §3.2b`：
  标题 + 右端 `{类型} · {N}分`、证据区（复用 `EvidencePanel`）、动作区 `[取消] [提交]`。
  **没有 reason 行、没有色条以外的装饰、不写任何说明文字**。
- `[提交]` 在 `evidence.length === 0` 时 `disabled`；点击后两颗按钮同时 `disabled`（本地 busy）。
- 失败（提交返回错误原文）→ 在卡片动作区下方一行显示原文，2.6s 消失（与审核卡同一个 `ERROR_MS`，不另造样式）。

`ChatData` / `ChatActions` 相应加：`pendingSubmit: Task[]`、`submitReview(taskId): Promise<string | null>`、
`cancelSubmit(taskId): Promise<string | null>`（`chatTypes.ts`）。`cancelSubmit` 内部 `transition({to:'doing'})`。

## 10. 测试（锁关键行为，不逐像素）

1. **状态机**：`todo → pending_review`、`doing → pending_review`、`pending_review → reviewing`、`pending_review → doing` 允许；
   `pending_review → done` 拒绝；`daily → pending_review` 拒绝。
2. **`hardGateOf`**：`requiresEvidence = false` 且证据 0 条 → 仍返回 `need_evidence`（这条锁的就是本单修的 bug，旧代码必红）。
3. **证据闸门**：`requiresEvidence = false` 的 `deadline` 任务直接 `task.complete` → 抛 `EVIDENCE_REQUIRED`。
4. **sweeper**：注入 `now`，`pending_review` 且 `updated_at` 为 11 分钟前 → 被退回 `doing`；9 分钟前 → 不动；
   `reviewing` 状态的任务**任何时间都不动**。
5. **`submitForReview`**：`transition` 失败时不调 `ai.review`（用 mock 断言零调用）。
6. **待提交列表**：排序按 `updated_at` 升序；`submittingIds` 里的任务即使已变 `reviewing` 仍留在列表。

注册表：`WIRED_CHANNELS` 数量不变（本单不加通道）。

## 11. 验收（两条主路径 + 一条回归，真机手点）

1. **证据链走通**：建一条限时任务（不勾任何东西）→ 右栏点完成 → **会话末尾出现待提交卡**，`[提交]` 是灰的 →
   传一张图 → `[提交]` 变亮 → 点它 → AI 判 `pass` → 任务沉到「已完成」、积分增加、卡片消失、审核卡上**一个可点的东西都没有**。
2. **取消与退回**：另建一条限时任务 → 点完成 → 卡片出现 → 点 `[取消]` → 任务回进行中、分数不变；
   再做一条 → 点完成后**什么都不做**，等 10 分钟 → 任务自己回到进行中。
3. **回归（本单修的那个 bug）**：建一条限时任务、不给任何证据 → 点完成 → 确认**不可能**直接拿到 `pass` 或加分；
   现在的正确表现是卡在待提交、`[提交]` 点不动。
