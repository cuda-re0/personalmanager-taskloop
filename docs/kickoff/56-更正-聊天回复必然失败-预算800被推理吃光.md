# 56 · 更正：聊天模式回复必然失败——800 预算被强制思考吃光（v0.56）

> **类型**：缺陷更正（走外部施工方）。
> **起因**：用户 2026-11-01 19:49 截图——聊天模式发「莉娜，从今天开始，你就是我的专属秘书了」，回复是红字「这次没读懂模型的回复，再试一次」。用户判断「聊天模式回复也被限制格式了」。
> **裁决**：用户选 **B 方案**（保留模型思考，调预算与超时），并要求额外加一条兜底：**正文为空时自动重试一次**。

## 1. 现象

聊天模式（`mode='chat'`）下任何一句都失败，落 `AI_PARSE_FAILED`，界面一句「这次没读懂模型的回复，再试一次」；点「重试」同样失败。

## 2. 根因（已实测，不是推测）

聊天走 `chatText`，**不套 JSON、不做 zod 校验、不带 `response_format`**，输出只做「剥围栏 → trim → 非空」。所以跟"格式"无关。

真正原因是 token 预算：

- `glm-4.7-flashx` 是**强制思考模型**。智谱文档（`docs.bigmodel.cn/cn/guide/capabilities/thinking`）：GLM-4.7 系列 `thinking.type` 默认 `enabled` 且为强制思考；响应里 `reasoning_content` 与 `content` 并列。
- **`max_tokens` 是 `reasoning_content` + `content` 的总和**，不是正文字数上限。
- 我们把聊天预算写死成 `CHAT_MAX_TOKENS = 800`（v0.42 至今）。推理一开口就吃掉 790+，正文返回空串、`finish_reason='length'` → `chatText` 判空 → `AI_PARSE_FAILED`。

**推理长度不随历史增长**（2026-11-01 20:16 实测，三组对照，均 `max_tokens=65536`）：

| 场景 | 推理 token | 正文 | finish |
|---|---|---|---|
| 无历史 | 540 | 78 | stop |
| 13 条真实历史 | 782 | 99 | stop |
| 重 system（12 条真实记忆 + 摘要 + 13 条历史） | 807 / 1214 / 1003 | 19~60 | stop |

峰值 1214，与历史条数没有线性关系，主要取决于内容复杂度。所以这不是「聊着聊着越来越糟」，而是**从 800 这个预算定下来的那天起，每一轮都必然失败**。重试无效，因为重试还是同一份 800 预算。

**另有一条独立失败路径**：`finish_reason='stop'` 但正文 0 字符（模型思考完什么都没说）。这与预算无关，调多大都救不了。真实记忆场景跑 3 次没复现（推理 807/1214/1003，正文正常），只在人为塞入占位式假记忆时触发过 1 次——属偶发。本单用「空正文自动重试一次」兜它。

**为什么一路没人发现**：03 §9.4 表里 `glm-4.7-flashx` 一直标「未实测 / 非推理」，而同一节下方白纸黑字写着「上线前必须实测三件事：① 它是不是非推理模型（响应里有没有 `reasoning_content`）」——这条实测从 W12 起漏做。§9.4 另一行 `glm-4.5-flash` 的备注「推理（`content` 空是 token 不够）」就是同一个坑，踩过第二次。

### 3.2 `chatText` 的重试规格（写死）

1. **最多发 2 次**（首次 + 重试 1 次）。第二次请求的 `messages` **原样重发，不加任何提示语**——空正文不是格式错，没有 issues 可回授，改 prompt 只会引入不确定性。
2. **空正文的判定责任从 `readOutcome` 挪到 `chatText`**：`requestText` 这条路径要允许拿到 `content=''` 的响应（例如给 `readOutcome` 加一个"允许空"的开关，只有 `requestText` 传允许）。`chatJson` 那条路径（`request`）**行为一个字不许变**。
3. **重试条件**：`stripFence(content).trim()` 为空，**且** `finish_reason !== 'length'`。
   - `finish_reason === 'length'` **不重试**，直接失败——同样的预算会得到同样的截断，这是 `chatJson` §2.2 已有的原则，`chatText` 沿用。
4. **第二次仍空** → 抛 `AI_PARSE_FAILED`，文案仍是 `AI_COPY.parseFailed`（**一个字不许改**），`detail` 里要能看出：末次 `finish_reason`、正文长度、**已重试 1 次**。
5. **取消（`signal` abort）不重试**：`AiAbortedError` 直接冒泡，第二次请求不许发。
6. **usage 累加**：两次的 `in` / `out` 都相加作为本次 `ChatTextResult.usage`；`latencyMs` 从**第一次请求发起**算到拿到正文为止（含中间那段）。理由：`tokens_in/out` 是落库的账单口径，必须是真实消耗。
7. `stripFence` / `trim` / 最终判空三件事**保持原样**，只是外面多套一层"最多 2 次"。

## 4. 为什么是 8000，不是 4000 也不是 65536

- 实测推理峰值 **1214**，8000 是 6.6 倍余量；4000 只有 3.3 倍，属于"够但不稳"。
- 不设上限（65536）虽不预扣费、也不会更贵，但等于放弃"防模型话痨"这层保险：聊天 UI 是逐字显现（40 字/秒），真出几千字会像卡死。
- 8000 对正常正文（40~200 token）构不成任何限制。
